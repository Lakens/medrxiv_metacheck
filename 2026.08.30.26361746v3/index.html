What we found

Show details

Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

It is possible that there is a true non-zero effect, but that the study did not detect it. Make sure your inference acknowledges that it is possible that there is a non-zero effect. It is correct to include the effect is ‘not significantly’ different, although this just restates that p > 0.05.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Introduction

Perioperative myocardial injury affects >25% of cardiac surgery procedures where it is the primary cause of early death, or results in delayed recovery, lower quality of life, and increased healthcare resource use.( 1) Decades of research have not delivered effective myocardial protection interventions. (2) (3) (4) (5) (6) Sodium valproate is a class I/IIa Histone Deacetylase inhibitor (HDACi) in widespread use for the treatment of neurological diseases that protects myocardium from acute metabolic stress in a wide range of pre-clinical models. (7) We hypothesised that pre-surgery administration of sodium valproate would have myocardial protection effects in people exposed to the severe metabolic stress of cardiac surgery.

Valproate has unpredictable pharmacodynamics where in vivo effectiveness is not directly attributable to plasma concentrations. Valproate also has both predictable (GI symptoms, reduction in platelet counts) and unpredictable (hepatotoxicity, pancreatitis) toxicity that affect adherence and safety. The trial was designed as a dose finding study with pre-specified adherence, safety, and pharmacodynamic outcomes. Based on the known biological effects of valproate, experimental analysis investigated whether treatment effects were attributable to changes in chromatin accessibility, (8) pro-survival gene expression, (7) (8) (9) or posttranscriptional modification of cellular injury responses (10) in myocardial biopsies from trial participants.

Immunofluorescence in myocardial biopsies

Post transcriptional mechanisms associated with cell death susceptibility were evaluated using immunofluorescence (IF) in right atrial biopsies from trial participants (Figure 4A).

In valproate ≤14 days biopsies, key cell protection signals in MYBPC3 positive cardiomyocytes including phosphorylated AKT1 (Ser473), acetylated p53 (K382), phosphorylated GSK-3β (Ser9), and GPX4 were all significantly elevated relative to controls (Figure 4B).

In valproate>14 days biopsies, GPX4 and pAKT were reduced in in MYBPC3 positive cardiomyocytes relative to controls, consistent with cytoprotective programme attenuation. In contrast, RIPK3, pMLKL, Cleaved Caspase 3 and 4-HNE were elevated, consistent with increased susceptibility to necroptosis, apoptosis, and ferroptosis (Figure 4C).

In vitro experiments

Next, we investigated whether valproate inhibits ferroptosis in vitro using IL-6+H₂O₂ treated, AC16 cardiomyocytes. These cells show enrichment for ACSL4, the enzyme that dictates cellular sensitivity to ferroptosis, and suppression of key effectors for alternative forms of programmed cell death including canonical necroptosis (RIPK3), intrinsic apoptosis (CASP9), and NLRP3-inflammasome pyroptosis (Figure 5A). They also demonstrate increased cell death (lactate dehydrogenase release) and lipid peroxidation (malondialdehyde release) versus controls in response to ischaemia reperfusion injury (IRI) that is inhibited by the selective ferroptosis inhibitor, Ferrostatin-1 (2 μM) (Figure 5B, C).

In IL-6+H₂O₂ treated AC16 cardiomyocytes, pre-treatment with valproate attenuated cell death and lipid peroxidation in response to IRI, with a similar effect size to Ferrostatin, (Figure 5B, C) Valproate pre-treatment increased AKT and p53 gene expression but not GSK3β (Figure 5D). Valproate selectively increased expression of p53 anti-apoptotic genes p21 (CDKN1A) and TIGAR with no increase in expression of the pro apoptotic genes BAX or PUMA (Figure 5E). siRNA knockdown of TP53 abolished valproate mediated TIGAR expression (Figure 5F) and cell protection (LDH reduction, Figure 5H). siRNA knockdown of AKT and GSK3β did not attenuate valproate mediated cell protection, pointing to posttranscriptional activation. Other key promoters of programmed cell death including RIPK3/ MLKL (necroptosis) or Casp-3 (apoptosis) were not affected by valproate (Figure 5I). Discussion

Main findings

A first-in-man evaluation of the HDACi sodium valproate in cardiac surgery, combined with multilevel characterisation of myocardial biopsies from trial participants and complementary in vitro experiments, suggests a myocardial protection effect of ≤14 days valproate treatment pre-surgery that is associated with activation of pAKT-pGSK3β (Ser9), acetylation of nuclear p53 (K382), and anti-ferroptosis GPX4 signalling in myocardium. In vitro, valproate prevented ferroptosis in AC16 cardiomyocytes in response to IRI by activation of the p53/ TIGAR/ GPX4 pathway.

In contrast, valproate treatment >14 days was associated with cardiomyocyte dedifferentiation, suppression of ferroptosis protection signaling, increased expression of necroptosis, apoptosis and ferroptosis susceptible networks, and increased myocardial injury post-surgery.

Interpretation

The effects of valproate ≤14 days were not explained by changes in chromatin accessibility, which likely reflect the short drug exposure in the trial. This is also consistent with our results showing the main effectors as post-transcriptional.

First, we showed increased p53 acetylation, a recognised effect of HDAC1/2 inhibition, previously shown to reduce p53 activity at pro-apoptotic genes promoters,(31) increase TIGAR expression and GPX4 activation, and reduce ferroptosis post IRI in non-cardiac tissue. (32) Second, DEG analyses showed combined suppression of PPARGC1A and MB with valproate ≤14 days. Both are targets of the PPARα/PGC-1α axis that governs mitochondrial fatty acid oxidation. One of the principal non-epigenetic actions of valproate is inhibition of β- oxidation through sequestration of free coenzyme A and carnitine.( 33) Inhibition of fatty acid oxidation in the adult heart promotes a less differentiated, more regeneration-competent cardiomyocyte state. (34) The accompanying reduction in myofilament accessory and M-band transcripts, without change in the core contractile genes, is consistent with this partial, reversible shift in cardiomyocyte phenotype rather than with loss of contractile apparatus. We observed this combined signature only with ≤14 days of treatment, alongside the cytoprotective signals described above, and it was absent after longer exposure.

Third, participants treated >14 days showed loss of SYNE1, a critical regulator of nuclear cytoskeletal mechanotransduction. Loss of SYNE1 is associated with a cardiomyopathy phenotype and increased susceptibility to injury through pro-apoptotic p53 target genes, consistent with our results.( 35) Together, these observations suggest that the early metabolic and cytoprotective adaptations to valproate are not sustained, and that prolonged exposure is accompanied by a distinct changes that increase myocardial injury susceptibility.

Ferroptosis is increasingly recognised as an important therapeutic target for the prevention of IRI in humans.( 36) However, there are currently no licensed clinical therapeutics for ferroptosis in humans. (37) Our results provide new evidence that ferroptosis is an important contributor of myocardial cell death following cardiac surgery. In addition, we show that valproate, a widely available, inexpensive, generic medication that is well tolerated by people waiting for surgery, is associated with increases in ferroptosis protection pathways and likely reduced troponin release in vivo. Future research will evaluate whether valproate pretreatment results in clinically significant reductions in myocardial injury via attenuation of ferroptosis.

Strengths and limitations

First, the ITT analysis did not demonstrate a treatment effect, and the as-treated analysis will have introduced significant bias, given our knowledge of the ITT results. In mitigation, using an ITT approach, when 38% of participants did not receive their minimum required treatment for the mechanistic analysis, would have introduced greater bias. The value of this approach was demonstrated by consistent findings across the as-treated analysis of troponin release and myocardial injury, multilevel characterisation of myocardial biopsies, and in vitro experiments. However, our findings cannot be considered causal as a result.

Second, the trial was terminated after completion of the experimental medicine and dose finding phase due to the exhaustion of available funds caused by the COVID19 pandemic.

Progression to a proof-of-concept efficacy trial is warranted based on these results.

Third, our pseudobulk analyses of snRNAseq and snATACseq were underpowered to determine treatment effects on chromatin accessibility and gene expression. We adopted rigorous quality control to mitigate the risk of ambient RNA contamination arising from fracturing of cardiomyocyte nuclei during freeze-thawing, but after quality control only 3 to 9 donors per group contributed to each pseudobulk analysis, and as few as 3 for cardiomyocyte RNA. Analyses at this scale are capable of detecting coordinated, pathwaylevel changes but not individual gene effects, and no gene reached an adjusted significance threshold in any contrast. The ferroptosis and p53 effector transcripts central to our proposed mechanism, including GPX4 and TIGAR, were not detected at levels permitting testing in in cardiomyocytes. As the analyses were only powered to detect large treatment effects (>2FC) we conclude that the transcriptomic data can neither support nor exclude regulation of these pathways in myocardium.

A final limitation is that right atrial biopsies have indirect generalisability to ventricular tissue. However, in our experience, the routine collection of adequate quantities of atrial myocardium is more consistent and reproducible than for ventricular tissue which is a key consideration in experimental RCTs where the numbers of participants are limited.

Conclusions

Pre-surgery administration of sodium valproate 15mg/kg/day ≤14 days is safe and well tolerated in cardiac surgery patients. The direction of the treatment effect on myocardial injury in vivo was consistent with myocardial protection. Multilevel characterisation of myocardial biopsies collected at surgery suggest post-translational effectors, including pAKT-GSK3β activation, and p53 acetylation/GPX4 prevention of post IRI ferroptosis as likely mechanisms. Longer duration treatment likely increased myocardial injury susceptibility via cardiomyocyte dedifferentiation and activation of pro-apoptotic, ferroptotic, and necroptotic signaling networks.
