To check Non-Significant P Value Check

What we found

We found 40 non-significant p values that should be checked for appropriate interpretation.

Show details

Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

It is possible that there is a true non-zero effect, but that the study did not detect it. Make sure your inference acknowledges that it is possible that there is a non-zero effect. It is correct to include the effect is ‘not significantly’ different, although this just restates that p > 0.05.

Metacheck does not yet analyze automatically whether sentences which include non-significant p-values are correct, but we recommend manually checking the sentences below for possible misinterpreted non-significant p values.

Patterns are designed to capture:

When a statement is expected

The module sorts each paper by where its data came from (the internal .data_source(); the signs and how the rule was tested are described in R/data-source.R): - own: the authors collected data from people or animals, for this paper, in an earlier study of their own, or (a protocol) will collect them; - existing_records: records about individual people that the authors obtained for this study, such as hospital records or a cohort; - existing_unclear: existing data about people from a source the module could not identify; - open_resource: an open resource any researcher can use, such as UK Biobank or NHANES; - none: no data about people or animals (a review, simulation, commentary, theory, tutorial, coding of published papers, or figures about groups); - uncertain: the signs were missing or pointed both ways; - no_text: the paper has no text.

How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. With the use of an LLM, it checks if the power analysis is reported with all required information.

The regular expressions can miss power analyses, or fail to classify them correctly. The type of power analysis is often difficult to classify, which can easily be solved by explicitly specifying the type of power analysis as ‘a-priori’, ‘sensitivity’, or ‘post-hoc’. Note that ‘post-hoc’ or ‘observed’ power is rarely useful. The LLM can fail to identify information in the paper, and will not have access to information in paragraphs in the paper other than those that contain the word ‘power’. This package was validated by the Metacheck team on articles in Psychological Science.

How Preregistration Check works

Retrieve information from preregistrations in a standardised way, and make them easier to check.

The Preregistration Check module identifies preregistrations on the OSF and AsPredicted based on links in the manuscript, retrieves the preregistration text, and organizes the information into a template. The module retrieves text from the OSF with its API, and from AsPredicted with ResearchBox’s API when a ResearchBox key is set (see rbox_token()), or else from the preregistration’s web page. The information in the preregistration is returned. An AsPredicted link that could not be read is named in the report, with the reason.

The module can’t extract information from non-structured preregistration templates (i.e., where the preregistration is uploaded in a single text field) and it can’t retrieve information in preregistrations that are stored as text documents on the OSF.

How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). When the sentence of a test says it is one-sided (“one-tailed”, “one-sided” or “directional”), a p-value that fits a one-sided test counts as consistent (statcheck’s OneTailedTxt setting; #695). When the paper says anywhere that its tests are one-sided, a p-value that fits a one-sided test in either direction counts as consistent too: half the two-sided p, or 1 minus that half for an effect against the predicted direction. Equivalence tests (TOST) are left out, as their p-values do not test the difference. A statistic written with “<” or “>” is read as a bound, and in a sentence about equal variances an F-test’s two-sided p (twice the one-tailed p) counts as consistent. For more information, see StatCheck.

This module only checks statistical results reported in the running text of the manuscript. It cannot (yet) process statistics reported only in tables.

This module was developed by Daniel Lakens and Lisa DeBruine

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A link to a file-sharing service (Google Drive, Dropbox, OneDrive, Box, WeTransfer, MEGA, iCloud Drive, Baidu Netdisk, SURFdrive; see [file_share_links()]) gets a warning and makes the light yellow: such services are not repositories, as files can be changed or deleted at any time, get no DOI, and the link stops working when the account is closed. The report advises a stable repository such as Zenodo instead. Their files are not read, and summary_table$file_share_n counts the links.

Deposits in archives for sequence and expression data (GEO, the INSDC archives BioProject, SRA, ENA and DDBJ, and ArrayExpress; see [seq_archive_links()]), mostly named by accession number, are read for whose deposit they are. The authors’ own are listed with what they hold ([seq_archive_size()]) and are not downloaded or checked as data and code; summary_table$archive_own_n counts them.

R packages on CRAN ([cran_links()], [cran_info()]) are the paper’s own when a paper author is a package author and the paper presents the package; the paper’s own are listed with their version and not checked (summary_table$cran_own_n). A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. When every linked deposit is set aside, the traffic light is “na”. A deposit that is the paper’s own is counted as such when its README, title or description names the paper (its title or DOI).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. A TRO uses them for each trov:TransparentResearchPerformance. * run_results$exit_status: the exit status of the process that ran the script (0 = ended normally); NA when the process did not report one (a time limit, or Docker failing to start the container). * artifacts: one row per file, with stage (deposit: as downloaded from the repository, hashed from the downloaded file; before_run: the run folder just before the first script ran, after metacheck’s own changes, such as rewritten paths and unpacked archives; after_run: only the files the scripts made (status new), changed (changed) or removed (removed), as an unchanged file is the one listed before the run), path (relative to the run folder, as valid UTF-8, a byte of another encoding written as <xx>), size (bytes), sha256, mime_type (by extension, NA when unknown), source (the file’s address in the repository, for deposit). The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Files metacheck itself copied or made between passes (see modifications, output_copied, file_placed) show in after_run too. A TRO uses the rows as trov:ResearchArtifacts and each stage as a trov:ArtifactArrangement. * modifications$sha256_before, modifications$sha256_after: the hash of the changed script as downloaded and as it ran; NA when the script is not at the same path in both (a script made from an R Markdown file). * environment: the system that ran the code (trov:TransparentResearchSystem in a TRO): metacheck_version, started_at, ended_at, host (R version, platform, operating system), sandbox, network_isolated (TRUE only when every Docker run had --network none; the process sandbox does not stop the network), internet, timeout_per_script, total_timeout, python_local (the Python run outside Docker and its version), and docker: runs (for each kind of run, r_run, r_install, python_run, python_install, the image and the docker run arguments, such as --network none, --read-only, --cap-drop ALL, no-new-privileges, the process limit and the memory and processor limits) and images (for each image, its ID and digests from docker image inspect, its creation time and the R and Python versions its environment declares).

run_results$checked says what the run of each script shows about the code, in five groups, so that a script that does not reproduce is kept apart from one the check could not test: ran (it ran to the end); code_error (it did not reproduce: it stopped with an error of the code or the deposit, could not be read, or needs a file the deposit does not hold); dependency (a package or program was not available: a package that could not be installed or was not loaded, a program outside R and Python, a system library, or R crashing in a package’s compiled code); time (it did not finish within the time limit for one script, or was not started because the time for all scripts had run out); and not_checkable (it could not be checked automatically: it needs a person, the internet, a key or another setting of the authors’ computer, one platform such as Google Colab, Windows or OpenSAFELY, more memory than the run allows, a file that was not downloaded, a screen, or a program that runs it, or it is a file of a package of the code that Python runs only as a module of that package). It is NA for files run inside another script, files that are not an analysis, files not read, and a Docker failure. summary_table counts each group (repro_ran_n, repro_code_error_n, repro_dependency_n, repro_time_n, repro_not_checkable_n), and the report’s first sentence gives them. The traffic light reflects the static readiness signals by default; a script in code_error that stopped with an error makes it red, as a script that crashes on its own analysis is a genuine reproduction failure, and a script in one of the other three groups keeps it from being green. Calls that need a screen, which the run does not have (dev.print(), dev.copy2pdf(), dev.copy2eps(), savePlot(), windows(), win.graph(), x11(), quartz(), View()), are replaced before the run by calls that need none, which modifications records as screen_call_replaced. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

The RetractionWatch Check module compares the reference list against studies in the RetractionWatch database based on the DOI. If a study in the database is found, a reminder is provided that the study was retracted, has an expression of concern, or a correction.

The module requires that the reference has a DOI: the DOI in the paper’s reference list, or one looked up with add_bib_match() before the module runs (see ref_table()). References without a DOI are not checked.

It is possible the authors are already aware that a study was retracted, but the module can’t evaluate this.

The database can be manually updated with the rw_update function. For more information, see https://gitlab.com/crossref/retraction-watch-data.

How Replication Check works

This module checks references and warns for citations of original studies for which replication or reproduction studies exist in the FLoRA database.

The Replication Check module compares the reference list against studies in the FLoRA (FORRT Library of Replication Attempts) database based on the DOI. If a study in the database is found, a reminder is provided that a replication or reproduction of the original study exists, and should be cited. No reminder is given when the paper already cites that replication or reproduction (matched by its DOI).

The module requires that the reference has a DOI: the DOI in the paper’s reference list, or one looked up with add_bib_match() before the module runs (see ref_table()). References without a DOI are not checked.

It is possible the original study was cited for other reasons than the empirical claim tested, or that the replication/reproduction in the FLoRA database is for only one of the studies in the paper, and not the study the authors discuss.

The database can be manually updated with the FLoRA_update() function. For more information, see https://forrt.org/FLoRA/.

Abstract

Background. Anthracyclines are widely used chemotherapeutics limited by dose-dependent cardiotoxicity. Because cardiovascular physiology and drug handling oscillate across the day, the timing of drug administration may influence cardiac risk. Optimal timing may depend on both an individual's internal circadian phase and environmental light exposure. We tested whether dosing time is associated with anthracycline cardiotoxicity, whether this is also true of overall treatment outcomes, and whether optimal dosing time is modified by photoperiod and the genetically predicted chronotype.

We analyzed ejection fraction (EF) change following anthracycline exposure in the All of Us research program (AoU; 70 patients) and incident heart failure (HF) in the Penn Medicine Biobank (PMBB; 843 patients). Dosing time was modeled on both clock-time and solar (timefrom-sunrise) axes using flexible splines, with likelihood-ratio tests (LRT) for association and for interaction with photoperiod and a germline chronotype polygenic score (cPGS). The cPGS was validated against wearable-derived midsleep and heart-rate rhythms.

Results. Dosing time was associated with anthracycline cardiotoxicity in both cohorts, with greater harm at later dosing times (AoU EF LRT p=0.011 clock, p=0.029 sunrise; PMBB HF p=0.052 sunrise, p=0.084 clock). No association was observed with non-HF mortality (p=0.75, 0.77), consistent with a narrowing of the therapeutic index. Photoperiod modified the dosingtime association (AoU p=0.064 clock, p=0.062 sunrise; PMBB p=0.023 clock, p=0.093 sunrise). Modification by cPGS was directionally consistent across cohorts but did not reach significance, likely reflecting attenuation of a polygenic proxy capturing limited chronotype variance.

Anthracycline dosing time is associated with cardiotoxicity but not mortality and is modified by photoperiod, identifying dosing time as a modifiable, circadian-sensitive factor. These findings motivate prospective, chronotype-and season-informed studies of anthracycline scheduling.

We would also like to thank the Penn Medicine BioBank team and Regeneron Genetics Center for providing genetic variant data for analysis.

Introduction

Anthracyclines are part of therapeutic regimens of multiple types of cancers. However, they are known to cause dose dependent cardiotoxicity.( 1) Because multiple aspects of cardiovascular and organismal physiology (including drug targets, metabolizing enzymes, and transporters) oscillate rhythmically throughout the day and night, it has been suggested that drug timing can influence their adverse effect profile.( 2, 3) Indeed, in a recent cohort study, patients receiving anthracyclines during the morning hours were at lower risk of developing cancer therapy related cardiac dysfunction compared to patients receiving their doses later in the day.( 4) Multiple clocks influence human chrono-physiology: the circadian clock (endogenous molecular clocks), the social clock (local time on a watch), and the solar clock (sunrise-sunset). (5) The solar clock varies through seasons and latitude, and the properties of the circadian clock (such as phase) varies between individuals. Chronotype is the behavioral manifestation of circadian rhythms in sleep/wake time preference. (5) In a GWAS study, 351 loci were associated with chronotype including core molecular clock genes such as PER1-3, CRY and ARNTL with an estimated heritability at ~ 14%.( 6) Seasonal changes affect the duration of melatonin secretion and shift its on-and offset times as well as roughly a quarter of genes in blood and metabolites in serum. (7, 8) Given these three clocks -circadian, social and solar -the question arises whether the optimal dosing time (where oncologic efficacy is maximal and cardiotoxic risk is minimal) is universal or depends on an individual's internal circadian phase and environmental context. Because clock time does not uniformly reflect internal biological time across individuals or seasons, the cardiotoxic effect of a given dosing hour may vary with chronotype and photoperiod.

In this study, we leverage the convergence of internal (genetic), social, and solar clocks on human cardiovascular physiology to test whether variability in the cardiotoxic effect of anthracycline dosing time can be explained by environmental photoperiod and an individual's chronotype Across two independent biobanks and using two distinct endpoints, we confirm that dosing time-of-day is associated with cardiotoxicity but not with non-heart-failure mortality. We show that this association is modified by photoperiod and to a lesser extent by genetically predicted chronotype, indicating that the cardioprotective dosing window is not fixed but shifts with an individual's seasonal light environment.

Results

Afternoon dosing increases the risk for cardiotoxicity with no significant effect on survival.

From the ejection fraction (EF) data of 70 patients receiving anthracyclines in the AoU research program, we find that dosing time-of-day is significantly associated with post treatment EF change (Likelihood ratio test, LRT p-value = 0.011) with an inverted J-shaped pattern (p-value for non-linearity LRT = 0.043) and significantly drops starting with dosing times around 4pm (Figure 1 A Left). We find similar results when we set our time variable as time from sunrise that changes across months and geographic latitude. (LRT p-value = 0.029, non-linearity p-value = 0.149, Figure 1A Right).

We then sought to validate the AoU findings on HF diagnosis in an orthogonal Electronic Health Record (EHR) dataset from the Penn Medicine Biobank (PMBB) consisting of 843 patients and 47 HF events (defined as the first appearance of a HF ICD code and a HF specific drug prescription within 7 days) over a median follow up time of 8.52 years. In the independent PMBB HF cohort the significant association seen in AoU was replicated directionally and shows trends mirroring those seen in the AoU EF data with an increase in risk later in the day. The association between clock time and HF risk trends towards significance, (LRT p-value = 0.084), while time from sunrise reaches nominal significance (LRT p-value = 0.052, non-linearity pvalue = 0.024, Figure 1B), consistent with lower power for a rarer binary endpoint.

We also examined non-heart failure death to test for a dosing time association with survival. We find no significant association when either dosing parameters were used (LRT p-values = 0.749 for clock time and p=0.767 for time from sunrise, 98 death events, Figure 2).

Thus, we find evidence suggestive of a non-linear association between anthracycline dosing time and cardiotoxicity with no effect on survival. This points to a potential effect on the therapeutic index of anthracyclines. Moreover, because confounding by patient acuity would be expected to track with mortality as well as cardiotoxicity, the absence of any dosing-time association with survival (the more-high powered outcome) argues against such confounding and indicates that our positive cardiotoxicity results are less likely to be biased by patient acuity. Supplementary figures 1 & 2 show how our sample was selected. Supplementary Tables S1 & S2 describe patient characteristics.

Photoperiod modifies heart rate rhythms

We sought to test whether the duration of the daily light period (photoperiod: sunset timesunrise time) modifies the dosing time-of-day association with anthracycline cardiotoxicity. We first validate that photoperiod affects other physiologic rhythms such as heart rate from AoU Fitbit data. We find a significant effect modification for the heart rate cosinor fits by photoperiod length using both clock time and sunrise time anchors (LRT p = <2e-16, Figure 3, Figure S3). Across photoperiod levels from the 5th to 95th percentile (9 to 15 h), the heart-rate rhythm amplitude increased modestly on both axes (clock: 7.58 to 8.05 bpm; sunrise: 7.81 to 8.05 bpm). On the clock axis, the acrophase was essentially stable across photoperiod (14.40 to 14.71 h), whereas on the sunrise axis it shifted markedly later with longer photoperiod, advancing from 7.26 to 9.32h after sunrise. This divergence indicates that the timing of peak heart rate tracks a relatively fixed clock hour rather than a fixed interval after sunrise, consistent with entrainment to clock/social time more than to the solar cycle. (9) Photoperiod modifies dosing-time-related anthracycline cardiotoxicity After relaxing the HF definition to only require the ICD code for HF to increase power for interaction tests (843 patients, 133 events), photoperiod also modified the dosing-time association, and within the data-dense interior this modification was directionally concordant across both outcomes. For interaction tests we set the significance level cutoff at 0.1, the threshold followed by Printezi et al.(4) The interaction was significant on both axes in AoU (LRT p = 0.064 clock, p = 0.062 sunrise), significant on the clock axis in PMBB (HF; p = 0.023), and on the solar axis (p = 0.095). Restricting interpretation to the middle of the plot where data are most abundant (as seen in the rugs on Figure 1), the hazard and EF heat bands align well: longer and shorter photoperiods sit on opposite sides of their respective nulls, with a crossover near mid-afternoon, such that elevated HF hazard corresponds to EF decline and reduced hazard corresponds to EF preservation (Figure 4). The biphasic, double-crossover appearance at the extremes of the heat bands coincides with the sparsely sampled edges. We therefore read photoperiod as a genuine effect modifier. The difference plots are shown over the full observed range (Figure S4). The results from the analysis applying the more stringent HF definition (47 events) show the same directionality but with higher non-significant p-values consistent with power limiting the detection of effect modification in a small event sample (Figure S5). We also tested whether the time-of-day association with non-HF mortality is modified by photoperiod and find no significant effect modification (interaction LRT p = 0.841 clock, p = 0.789 sunrise, figure S6). In addition to shedding light on the therapeutic window, these mortality results also serve as a control against illness acuity.

Chronotype polygenic score (cPGS) tracks device-measured circadian phenotypes

We next sought to test the effects of chronotype on the dosing time association with cardiotoxicity. Because wearable-derived chronotypes were available in only a small subset of anthracycline-exposed AoU participants who had EF data and were entirely absent from the PMBB validation cohort, we built a chronotype polygenic score as a harmonized, temporally antecedent proxy available in both genotyped cohorts. As a germline instrument, PGS is fixed before exposure and cannot be altered by chemotherapy or cardiac dysfunction, mitigating reverse causation inherent to post-treatment phenotypic chronotype measures.

We built the cPGS using the LDpred2 pipeline from GWAS summary statistics of chronotype in the UK-biobank. (10, 11) Because the UK-biobank participants are mostly of European ancestry while the AoU and PMBB have more diverse participants, we adjusted the cPGS using genetic ancestry principal components (Figure S7, Figure S8). After adjusting the cPGS for genetic ancestry, we tested it on a linearized midsleep time scale (a numeric chronotype measurement defined as the midway point between sleep onset and awakening) from AoU Fitbit data of 62,930 participants. We find that a higher ancestry adjusted cPGS significantly associates with later midsleep times (covariate adjusted p<2e-16, Figure 5A). We also tested the effects of the cPGS on continuous Fitbit heart rate data, another related wearable data stream available in AoU. We find significant effect modification by the cPGS (p<2e-16) when both sunrise and clock times are used as time anchors with a phase delay of about 0.5 hours in the later chronotype participants (peak heart rate at 14.8h, at the 95 th percentile cPGS Figures 5B and 5C) compared to earlier chronotype participants, (peak heart rate at 14.3h, at the 5 th percentile PGS). We plot the differences between the 95 th and 5 th PGS percentiles in supplementary Figure S9. We thus validate our polygenic score and establish that participants with later genetically predicted chronotypes have later midsleep times and phase delayed heart rate rhythms compared to participants with earlier chronotypes.

Chronotype polygenic score does not significantly modify dosing-time-related anthracycline cardiotoxicity

Across both biobanks, chronotype PGS did not significantly modify the anthracycline dosing time-cardiotoxicity association, though the heat bands were directionally consistent across cohorts. In AoU, the cPGS interaction was not significant on either axis (LRT p = 0.538 clock, p = 0.547 sunrise). The EF heat bands were nonetheless sinusoidal with a single midday crossover: later-chronotype individuals (high PGS) showed greater EF decline with morning dosing and relative preservation with early-afternoon dosing, while earlier chronotypes showed the reverse (Figure 6A). The PMBB HF surfaces mirrored this pattern once the opposing harm conventions are accounted for (elevated HR ≈ EF decline; HR <1 ≈ EF preservation, Figure 6B), with elevated HF hazard for later chronotypes at morning dosing resolving through the null by midafternoon and a single crossover at approximately 14-15 h clock time (≈8-9 h after sunrise), although the PcGS interaction was likewise not significant (p = 0.159 clock, 0.175 solar). This directional convergence of a continuous echocardiographic endpoint and an independent incident ICD-coded endpoint, despite differing populations and confounding structures, is consistent with a "circadian misalignment" interpretation in which dosing discordant with chronotype could be associated with worse cardiac outcomes while aligned dosing appears relatively protective; however, because neither interaction reached significance, we regard this as hypothesisgenerating rather than confirmatory. Isolating such an effect will likely require direct phenotypic measurement of chronotype, which would reduce the attenuation inherent to a polygenic proxy that captures only a fraction of chronotype variance. We show difference plots between the 95 th and the 5 th PGS percentiles in Figure S10.

Fitting the models applying the stringent HF definitions produces similar results (Figure S11). The chronotype PGS also does not significantly modify the time-of-day association with non-HF mortality (Figure S12).

Discussion

We show that the cardiotoxic effect of anthracycline dosing time is not fixed but is modified by seasonal light environment and, to a lesser degree, internal circadian phase. Across two independent biobanks and two distinct endpoints, dosing time was associated with cardiotoxicity but not with non-heart-failure mortality. This is consistent with a change in the therapeutic index rather than confounding by patient acuity, and this association was modified by photoperiod and, directionally, by genetically predicted chronotype. These results support the trend reported by Printezi et al. that later time-of-day dosing associates with higher cardiotoxicity risk, (4) and complement their echocardiographic analysis with EHR diagnostic data, ejection fraction changes, and a mortality endpoint. Although animal pharmacokinetic studies (12, 13) led us to hypothesize reduced morning efficacy, we found no association between dosing time and mortality, consistent with recent R-CHOP data showing no significant effect of dosing time on survival after adjustment (14). While overall survival is a commonly reported outcome in oncology efficacy studies, it is a crude measure of efficacy.

Longer photoperiods were associated with larger heart-rate rhythm amplitude, consistent with a more active daytime phase. (15) Peak heart rate remained anchored to a fixed clock hour rather than a fixed interval after sunrise, indicating entrainment predominantly to social/clock time over the solar cycle, in keeping with the influence of socially scheduled activity on cardiovascular rhythms. Photoperiod appeared to modify the dosing-time association more strongly on the clock axis, yet, as with heart rate, it shifted both the magnitude and timing of peak and trough risk. This supports assessing both clock and solar time for insight into the role of diurnal rhythms for parsing benefit-risk ratios.

A later genetically predicted chronotype was associated with a phase delay in the heart-rate rhythm, validating the score against a physiological readout. The chronotype × dosing-time interaction was directionally consistent across both biobanks with later-predicted chronotype patients appearing relatively protected against later dosing, consistent with prior chronotype literature. (16, 17) This association did not reach significance in either cohort. Because chronotype heritability is only ∼14%, (6) a polygenic proxy captures limited variance and likely underestimates the effect; direct phenotypic measurement would provide a more powerful test. Conversely, a germline instrument is fixed before exposure, better approximates a causal effect, and is immune to reverse causation. The consistent directionality across cohorts motivates adequately powered studies using measured chronotype.

A strength of this work is triangulation across independent data types (two biobanks, two cardiotoxicity endpoints, and wearable physiology), such that convergent signals are difficult to attribute to any single cohort. The null mortality association provides a specificity control against confounding by patient acuity. Our exposure-antecedent PGS, built from an independent dataset (UK Biobank) and validated against behavioral (midsleep) and physiological (heart-rate acrophase) readouts, is protected against reverse causation and harmonizable across cohorts lacking wearables. Modeling both clock and solar time guards against wall-clock artifacts.

Limitations include modest, event-limited sample sizes that limit power for the interaction analyses in particular; the PMBB chronotype interaction was directionally concordant with AoU but did not reach significance, though because the polygenic score captures only a fraction of chronotype variance this attenuation is expected to bias interaction estimates toward the null. As an observational study, dosing time was not randomized, and residual confounding from factors associated with both administration timing and outcome cannot be excluded. Exposure and outcomes were derived from real-world data, with anthracycline dose estimated through per-administration counting and doxorubicin-equivalent conversion, and with heart failure and ejection fraction subject to coding, surveillance, and ascertainment biases. Even though we adjust for each of these biases in our models we decrease the risks but do not eliminate them. The polygenic score was derived from a predominantly European-ancestry GWAS, and despite ancestry adjustment its portability across the diverse study populations is imperfect, while geolocation-based estimates of sunrise and photoperiod introduce additional measurement error. Finally, our analyses characterize associations and effect modification but do not causally establish that re-timing administration reduces harm, which will require prospective evaluation.

Conclusion

Across two independent biobanks and two distinct endpoints, delayed anthracycline dosing was associated with greater cardiotoxicity but not with non-heart-failure mortality, consistent with a narrowing of the therapeutic index rather than confounding by patient acuity. This dosing-time association was modified by photoperiod, while modification by genetically predicted chronotype, though directionally consistent across cohorts, did not reach significance. Together these findings suggest dosing time as a modifiable, circadian-sensitive factor in anthracycline cardiotoxicity and motivate prospective, chronotype-and season-informed studies to test whether optimizing the timing of drug administration can reduce cardiac harm.

Methods

Datasets and Ethical Approval

Data for this study was obtained from the All of Us research program (AoU, data version 9) including 535,662 genotyped participants (WGS) and the PennMedicine Biobank (PMBB, data version 4) including 70,493 genotyped participants (genotype array). NE is a credentialed user of the AoU program. AoU research procedures are approved by the AoU IRB and patients provide informed consent before participation. The AoU program determined that use of its data by credentialed users does not constitute human subject research and does not require IRB review. NE applied for and received access to the PMBB data (project ID: 1127). The PMBB is approved by the IRB at the University of Pennsylvania (protocol# 813913) and patients provide informed consent before participation. Our analysis of the PMBB data was deemed exempt from IRB review by the IRB at the University of Pennsylvania (protocol# 859892). For both datasets, only de-identified data was accessed and analyzed.

Dosing Time and Anthracycline Cardiotoxicity

From both datasets, we selected patients with documented anthracycline exposure of the following drugs: doxorubicin, epirubicin, daunorubicin, idarubicin, and mitoxantrone. We excluded patients who received a liposomal formulation of the drugs, had a non-systemic administration (intra-arterial chemoembolization or intravesical administration), received doses outside 07:00 to 23:59, who had diagnoses where a prolonged infusion may be indicated (Ewing sarcoma, multiple myeloma, Burkitt lymphoma, osteosarcoma, soft tissue sarcoma, liposarcoma, leiomyosarcoma, synovial sarcoma, fibrosarcoma, angiosarcoma, rhabdomyosarcoma, myxofibrosarcoma, pleomorphic sarcoma, diffuse large b-cell lymphoma, primary mediastinal lymphoma), and where we could not estimate the anthracycline dose. These exclusions decrease the risk of confounding by indication. The ability to estimate the anthracycline dose increases confidence that a patient received the dose at the associated timestamp.

Anthracycline dose was estimated by counting each recorded administration day as one dose of the regimen's published adult per-dose amount (mg/m², lower bound if a range) (18) and converting other anthracyclines to doxorubicin-equivalents (epirubicin 0.8, daunorubicin 0.6, idarubicin 4.5, mitoxantrone 10.5).( 4) Regimens were identified from anti-neoplastic partner drugs given within 2 days of the anthracycline (with dosing intervals used only to distinguish identical drug combinations), and unresolved administrations were imputed to match a patient's other administrations. Including cumulative dose in our models thus helps adjust for the cancer type and treatment regimen.

Dosing time was either determined as the timestamp reported in the EHR for drug administration or as time from sunrise. Sunrise time was calculated using the R package 'Suncalc' based on date and longitude and latitude. For the PMBB that has data from a Philadelphia based health system, longitude and latitude were fixed at -75.1652 and 39.9526. Because AoU contains data from patients across the United States each person's longitude and latitude was estimated from population weighted Zip code centroids. A cumulative mean time weighted by total cumulative dose contribution was then calculated for each dose.

In PMBB outcomes were defined as the earliest occurrence of an ICD code for heart failure (I42.7, I43, I42.9, I50.4, I42.0, I50.9, I42.8, I50.8, I50.2) that is accompanied by a HF specific drug prescription within 7 days. HF-specific drugs included: sacubitril/valsartan, mineralocorticoid receptor antagonists (spironolactone, eplerenone, finerenone); epithelial sodium channel (ENaC) blockers (amiloride, triamterene); ivabradine; vericiguat; digoxin; dobutamine; milrinone; loop diuretics (furosemide, bumetanide, torsemide, ethacrynic acid); and thiazide and thiazide-like diuretics (chlorothiazide, metolazone). The addition of HF drugs to the definition of HF increases the specificity of our outcome assessment. Patients with HF codes prior to their first dose were excluded. We then fitted Cox proportional hazards models with time varying covariates with each period in follow up starting at the chemotherapy cycle time and ending at either the next administration or at censoring. The dosing time variables were included as penalized splines. The models were adjusted for cumulative anthracycline dose, an indicator for daylight savings time, age, sex, the number of days with EHR encounters (controlling for detection bias), and the first 3 genetic ancestry principal components. To avoid overfitting with a small event number, we limited the covariate list to the above. We censored at the date of the last EHR encounter on record, death, or HF incidence. The proportional hazards assumption was tested using Shoenfeld residuals. To test whether the dosing time variable significantly associated with HF risk, we ran likelihood ratio tests comparing the fully adjusted models with and without the time variables. We then plotted the model fits with 95% confidence intervals using the coefficients and the covariance matrices.

From the AoU dataset, we used ejection fraction (EF) values reported from cardiac imaging modalities. We excluded patients with a minimum EF lower than 50% for the period before the first dose. We divided the follow-up time into periods starting with each chemotherapy cycle and ending with either the next cycle or, for the final cycle, the end of available echocardiographic follow-up, and assigned each echocardiogram performed after a cycle's administration (up to and including the next administration day) to that cycle, retaining the lowest ejection fraction per period. Periods without an echocardiogram were excluded from the analysis, but their doses were still counted toward the cumulative dose. We then fit mixed effects regression models with the percent change in EF from baseline as the dependent variable and the natural spline terms of the dosing time variables with 3 degrees of freedom as the independent variable of interest. Covariates included in the models were: cumulative dose, sex, age, baseline EF, the time of the nadir EF from the first dose, the number of EF measurements in the period, a daylight savings time indicator, and the first 2 genetic ancestry principal components. Similar to the PMBB analysis above we tested the significance of the dosing time association using likelihood ratio tests and plotted the model fits with 95% confidence intervals.

Building and Testing the Chronotype Polygenic Score

We obtained publicly available summary statistics from a GWAS for chronotype (phenotype 1180 in the UK biobank with levels of: Definitely a morning person, more morning than evening, more evening than morning, and definitely an evening person).( 19) The GWAS was run on 301,143 participants, included 1,0894,596 variants, and was adjusted for age, sex, and the first 20 ancestry principal components. (10) From these statistics we used LDpred2-auto to compute polygenic score coefficients that account for linkage disequilibrium based on the HapMap3 plus reference panel. (11) This resulted in 1,385,528 variants contributing to our polygenic score (PGS).

Based on the availability of genetic data, we used whole genome sequencing data in AoU and imputed array data in the PMBB (1,354,610 matched variants). We included variants with a genotype missingness rate of < 10% and a minor allele frequency ≥1% thus retaining1,261,731 variants in Aou and 1,246,331 variants in the PMBB. For individuals with missing variant genotypes we used applied mean imputation. We use the BigProdVec function from the bigsnpr R package to multiply each PGS coefficient with its corresponding variant genotype. The PGS was adjusted for genetic ancestry. Within each dataset, we regressed the PGS on the first 16 principal components (PCs), then modeled the squared residuals on the same PCs using a gamma generalized linear model with a log link to keep predicted variances positive. The adjusted PGS was each residual divided by the square root of its predicted variance, giving an approximately mean-zero, unit-variance score across ancestry backgrounds. (20) We then tested the adjusted PGS using sleep Fitbit data available in the AoU program from 62,930 participants. Of these we selected genotyped participants with at least 8 weekend days of data and who did not have sleep onset times between 06:00 and 18:00 or sleep durations <3h or >15h thus retaining 47,994 participants. We used the circular package in R to calculate each person's mean midsleep time (midpoint between sleep onset and awakening) and then transformed the circular midsleep to a linear variable with increasing midsleep time by subtracting 12 from midsleep times at night before midnight and adding 12 to those after. We then plotted the adjusted PGS percentiles against the mean and confidence interval of the midsleep of each percentile and fit a linear model for midsleep adjusted for age, sex, and the first 10 PCs.

Effect Modification by Chronotype PGS and Photoperiod.

We calculated photoperiod by subtracting sunrise time from sunset time obtained from the suncalc package. For each timing axis (clock time and solar phase, i.e. hours after sunrise) and each candidate modifier (chronotype PGS and photoperiod), we fit a model with the naturalspline timing term (3 df) entered additively with the modifier and a model with a full timingspline × modifier interaction and compared the two by likelihood-ratio test (3 df) to assess effect modification. For interaction tests we use a p-value cutoff of 0.1 because interaction tests are usually underpowered.( 4) We used the same model structures we used to test for the time-of-day association with cardiotoxicity above. Because interaction tests are usually underpowered, we expanded the definition of heart failure in the PMBB to only include the presence of an ICD code for HF. We adjusted for the same covariates as above except for including only 1 PC for models testing modification by cPGS and no PCs for models testing photoperiod modification.

We visualized the fitted interaction as a continuous heat band by predicting the outcome (log hazard ratio in PMBB, predicted % EF change in AoU) over a grid of dosing times crossed with the modifier evaluated from its 5th to 95th percentile in 2.5% increments, holding covariates at reference values (medians for continuous covariates, the modal level for categorical ones), and shading each timing × modifier cell by the modifier value. PMBB predictions are expressed as hazard ratios relative to a single common reference (median timing and median modifier) on a log scale, and the band was drawn over the 1st-99th percentiles of observed dosing time so that sparsely sampled tails did not obscure the interior pattern. This corresponded to 15 th to 85 th percentiles of observed dosing time in AoU.

To summarize the strength of modification across dosing time, we contrasted the high-versus low-modifier prediction (95th vs. 5th percentile) at each timing value and plotted this difference with a pointwise 95% confidence interval. The contrast and its variance were obtained from the difference in model design matrices multiplied by the coefficient vector and its covariance matrix, yielding the log-HR difference (exponentiated to a hazard ratio) in PMBB and the difference in predicted % EF change in AoU; these plots were drawn over the full observed range of dosing times, with a rug showing the per-patient data density.

Heart Rate Rhythm Modification by Chronotype PGS and Photoperiod

We extracted minute level Fitbit heart rate data from AoU participants with at least 7 days of monitoring (61,693 participants). We averaged all hourly measurements for every person-datehour combination. We calculated sunrise and photoperiod in similar ways as above using the suncalc package.

We modeled person × time-bin mean heart rate (weighted by the number of contributing observations) using linear mixed-effects models (lmer) with a cosinor parameterization, representing time-of-day by paired 24-hour cosine and sine terms on two axes: clock hour and hours from sunrise. Each model included a per-person random intercept and was adjusted for sex, birth year, and the first ten genetic principal components; and a modifier (chronotype PGS, photoperiod) interacted with both cosine and sine terms. Effect modification of the rhythm was tested by likelihood-ratio test (2 df) comparing an additive model to the cosinor × modifier interaction, both fit by maximum likelihood. For visualization, model-predicted heart rate (random effects set to zero) was computed over a grid of times of day crossed with the modifier from its 5th-95th percentile, holding covariates at reference values, and rendered as a heat band shaded by modifier value with a shared color scale and y-axis across panels. From the interaction coefficients we derived rhythm amplitude (√(β_cos² + β_sin²)) and acrophase (atan2(β_sin, β_cos), rescaled to hours) at the 5th, 50th, and 95th modifier percentiles.
