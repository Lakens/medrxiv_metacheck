An a priori power analysis for an independent samples t-test, conducted using the pwr.t.test function from pwr (Champely, 2020), indicated that for a Cohen’s d = 0.5, an alpha level of 0.05, and a desired power level of 80% required at least 64 participants in each group.

For a sensitivity power analysis, this sentence would look like:

A sensitivity power analysis for an independent samples t-test, conducted using the pwr.t.test function from pwr (Champely, 2020), indicated that with 64 participants in each group, and an alpha level of 0.05, a desired power level of 80% was reached for an effect size of d = 0.5.

How Ethics Approval Check works

This module searches for statements of ethics approval, IRB approval, institutional review board approval, and related terms.

Patterns are designed to capture:

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. Abstract

Gene-by-environment (GxE) interactions inform where genetics and environment converge to impact human health and disease. However, systematically mapping GxE interactions has been challenging due to the diversity of testable exposures and a lack of scalable approaches to measure the environments cells experience in vivo. Here, we identified modules of correlated plasma metabolites and proteins and used them as quantitative proxies for environmental exposures experienced by circulating leukocytes. We demonstrated that these proxies are associated with environmentally-modifiable clinical traits such as diet and infection and support broad mapping of geneby-environment (G × E) interactions affecting gene expression and CpG methylation in leukocytes. We identified significant interactions for 95.2% of tested genes and 5.9% of tested methylation sites. These G × E interactions showed specificity to exposures and cell type. Colocalization analysis further provided links between interactions and complex trait and disease loci. Finally, we expanded G × E interaction mapping to unexplored cell 1.

1 Introduction

Genome-wide association studies (GWAS) enable identifying genetic variants linked to complex traits and disease. However, GWASes often do not account for environmental contexts and can miss genetic variants whose effects are modified by the environment. Investigating these G × E interactions has been challenging due to a several reasons. Traditional G×E studies typically test for interactions with predefined environmental variables, such as self-reported diet, smoking status, and exercise-induced changes 1-5 . In addition, detecting a G × E interaction requires approximately four times the sample size needed to find a direct genetic or environmental effect of the same strength, increasing the cost of such studies 6 . Furthermore, these approaches are often restricted in scope to a few cell types or environments, limiting their ability to systematically capture G × E interactions across the body.

One opportunity to address the bias of pre-defined environmental variables lies in using blood plasma itself, as the variance in the blood plasma metabolome and proteome is largely influenced by environmental factors [7] [8] [9] . For instance, although variation in blood carbohydrate levels is partially genetically determined, it is mostly driven by environmental exposures such as meal timing.

Furthermore, studying gene-by-environment (G×E) interactions effects on molecular phenotypes such as gene expression and methylation has previously demonstrated improved power to identify variants where genetics and specific environments converge to affect gene regulation. [10] [11] [12].

We take advantage of both of these opportunities and use the axes of variation in the plasma metabolome and proteome as environmental proxies for the discovery of G × E quantitative trait loci for molecular phenotypes (gene expression and methylation). Using multi-omic data from the Multi-Ethnic Study of Atherosclerosis (MESA) 13 , we derive co-varying modules of blood plasma metabolites and proteins (which we refer to as "Molecular Exposure Modules", or MEMs) and use them as proxies for environmental states. We propose that these major axes of variation in the plasma metabolome and proteome represent the major exposures experienced by individuals. By quantifying interactions between these MEMs and the genome, we map G × E effects on cell type specific gene expression and DNA methylation and identify pervasive interaction effects. We then link interactions to complex traits through colocalization, bridging genetic variants, molecular environments, gene regulation, and complex traits. This approach provides a comprehensive multi-cell-type landscape of G × E effects across the leukocyte transcriptome and methylome.

2 Results

2.1 Axes of molecular variance in blood plasma

To systematically map G × E interactions, we developed an integrated multi-omic workflow utilizing data obtained from MESA (Fig. 1A). We chose to focus our analysis on the data from participants with complete multi-omic profiles(N=541; Fig. 1B; see Methods 4.1). When samples were collected, blood plasma and blood leukocytes were separated; blood plasma was retained for metabolomic and proteomic profiling (see Methods 4.2), and blood leukocytes was retained for transcriptomic and methylomic profiling 12.

To study the main axes of variation of the metabolome and proteome, we performed a weighted gene co-expression network analysis (WGCNA) on the proteome and metabolome (see Methods 4.3).

We refer to the resulting modules as MEMs, as they primarily represent the molecular exposure [7] [8] [9] to which blood cells are exposed. The WGCNA analysis resulted in a total of 52 metabolic MEMs, and 18 proteomic MEMs. WGCNA links metabolites/proteins to a single MEM, thus enabling a high degree of explainability for each MEM. Furthermore, we can characterize each MEM by its components, testing to see if a MEM's components are enriched in a specific annotation (see Methods 4.4; Extended Fig. 1; supplementary tables 1 and 2). On average, each metabolomic MEMs captures 51% of the percent variance explained (PVE) within its module, and combined they explain 37.1% of the PVE across the entire metabolome. Each proteomic MEMs captures on average 11.8% of the PVE within its module, and a total 10% of the PVE across the entire proteome (Fig. 1C; see Methods 4.5).

To test for cross-ome redundancy, we performed pairwise correlations, finding no pair of MEMs has a meaningful correlation (R² > 0.01), indicating that MEMs represent distinct information (Extended Data Fig. 2).

2.2 Discovery of Gene by Molecular Exposure interactions

We tested whether genetic variants associated with altered gene expression and methylation were interacting with molecular exposure defined by MEMs. We employed a G × E analysis, utilizing MEMs as the environment (see Methods 4.8). Applying this approach, out of the 16,750 tested genes, we identified 15,953 (95.2%) unique eGenes with a G × E interaction. For CpG methylation sites, out of a total 159,161 tested CpG sites, 9,472 unique G × E CpG sites (5.9%) harbored a G × E interaction. This analysis was performed for each cell type, across all MEMs. Overall, this rate of discovery is similar to what was previously reported: previous evidence shows that 32.2% of genes exhibit G × E interactions 11 , and 3.2% of methylation sites 16.

Importantly, our higher discovery rate might be attributable to the higher scale and statistical power of our analyses. Specifically, we analyzed data from more individuals than the prior studies (541 versus 249 for eGenes, and 149 for methylation sites). We also examined a broader range of cell types (6 versus 1) as well as environments (70 versus 4). Together, all these factors likely increased our ability to detect significant associations. Overall, these findings suggest that G × E effects on gene expression are observed widely. To examine the validity of the observed G × E interaction, 5.

2.3 Genetically Associating Molecular Exposure Modules with Complex Traits

Following our analysis of the factors governing G × E interactions, we sought to understand whether these interactions were relevant to human traits, especially diseases. To explore this goal, we performed colocalization analysis between human genome wide association studies (GWAS) 20 and the G×E interactions identified here (see Methods 4.12). 3 Discussion

Efforts to map G × E interactions have largely relied on either in vitro stimulation, for example by exposing cell lines to immune modulators 11, 24, 25 or on mapping interactions with broad epidemiological variables such as age, BMI, and diet [26] [27] [28] . The first offers causal mechanistic clarity but limited 11 . scope; the second captures real-world tangible variation but lacks explainability and molecular resolution. A third approach, testing interactions with individual metabolites or proteins across the entire metabolome/proteome would be prohibitive due to the correlated structure of each measurement and multiple testing. None of the approaches mentioned provides a scalable framework to systematically connect the molecular environment a cell experiences in vivo to its molecular phenotype.

Thus, in this work, we took a complementary approach. We systematically quantified G × E interactions across omic-layers using the plasma metabolome and proteome as quantitative proxies for the molecular exposures that blood leukocytes are exposed to in vivo. We constructed our quantitative proxies for molecular exposures in an unsupervised manner via network analysis using WGCNA, and called them Molecular Exposure Modules (MEMs). MEMs provide a framework to simplify the metabolome and proteome, offering a degree of explainability, as each metabolite/protein is assigned exclusively to a specific MEM, which allows a later over representation analysis to annotate each MEM. For example, we found MEMs associated with fatty acid metabolism and inflammation.

Next, we tested the effects of genotype-by-MEM interactions on cell type specific gene expression and methylation across 541 individuals from MESA. Characterization of the G × E interactions revealed that G × E are not centralized to a specific gene, CpG site, cell type, or MEM. Rather, the data indicates that G × E interactions are pervasive, occupying a spectrum of specificity, with methylation G × E interactions tending to be more cell-type specific. Moreover, an additive pattern emerges: molecular phenotypes (either gene expression or CpG methylation) for which a G × E interaction is found with multiple MEMs, are observed to be associated with multiple proteomic and metabolomic MEMs, and with multiple cell types. However, the strongest predictor of whether a gene will harbor a G × E interaction is simply whether a genomic main effect is discovered for that gene in that cell type. Among all cell types examined, B cells were found to have the highest number of detected unique molecular phenotypes per context, both with and without adjustment for potential covariates, and despite their limited proportion in the samples. This suggests that B cells are either the most environmentally responsive cell type, or alternatively, that a systematic bias is inflating false positives in B cells. Overall, these observations improve our understanding of the governing rules of context-dependent genetic regulation.

Currently, profiling G × E interactions across all cell types and molecular exposures is prohibitive for many reasons, including computational complexity, limited statistical power, and cost. We sought to demonstrate that the structure of G × E interactions is not random but learnable. By utilizing a zero-shot transfer learning framework trained on G × E interaction patterns, we show G × E interactions are predictable in a held-out cell. This provides a path towards scaling up the discovery of G × E interactions across the body when plasma proteomics and metabolomics are collected alongside multi-tissue multi-omics data. Further, as the number of cell types with characterized molecular profiles expands with the rise of single cell technologies [29] [30] [31] [32] , together with the increase in proteomic/metabolomic profiling 33 , predictive frameworks may enable the scaling of G × E mapping into new cell types.

As mapping molecular G × E interactions has enabled the discovery of "missing regulation" for complex traits and diseases, we also demonstrate how our approach can systematically uncover G×E effects contributing to health and disease. Colocalization with complex trait GWAS signals indicated that several of our G × E interactions may contribute to human phenotypes. Across a range of complex traits, we saw a median of 68.8% of colocalizations due to G × E interactions. We see this work enabling more systematic linking of molecular environment-dependent molecular regulation to disease-relevant genetic architecture. This work has several limitations. Regarding statistical power and design, our sample size (N=541), while large relative to comparable studies 6 , remains modest for G×E mapping. Our analysis is also cross-sectional and regresses out the effects of sex and ancestry. Further, current technologies do not capture all metabolites and proteins. Moreover, we do not account for heterogeneity in the biological importance of different metabolites and proteins, and we are limited in the scope of cell type deconvolution to abundant leukocytes. Regarding methodological limitations, we expect that further adaptations of our zero-shot prediction model may benefit from integrating prior knowledge, such as known eQTLs, regulatory annotations, or external databases. Furthermore, the colocalization procedure we employed is conservative, as we did not use variant bayesian fine-mapping 34 nor account for cross-MEM pleiotropy 35 . Moreover, as with many G × E studies, we do not establish causal directionality between the environment (MEMs) and molecular phenotypes, although MEMs might be a heritable trait of blood leukocytes. This is similar to G × E, in which BMI is modeled as the environment, although BMI has high heritability 36, 37.

In conclusion, we present a map of gene-by-environment interactions with the plasma molecular environment, revealing widespread context-dependent genetic regulation. Constituting one of the most comprehensive multi-omic G × E mapping efforts to date, this work is a step towards understanding how the genome, and molecular exposures affect phenotype. We chose to focus only on participants who have both exam 1 and 5 data. As part of the pilot study, a subset of participants was profiled using a multi-omic framework, including plasma metabolomics (6,052 metabolites) and proteomics (1,317 proteins), as well as RNA sequencing and DNA methylation measurement to capture gene expression and methylome epigenetic variation. The samples from MESA participants were selected for the TOPMed multi-omic pilot study due to the availability of previously collected specimens and the high ancestry diversity of the cohort. In addition, genotype data is available for all individuals in the multi-omic study. After harmonizing and intersecting samples across all molecular modalities and both exams, a total of 541 participants had complete data across all omes at both time points, forming a deeply phenotyped cohort, used for an integrative multi-omic study of the genome and molecular exposome 13, 38 . For a detailed outline of methods and quality control for MESA, refer to the supplemental methods section in 12.

The MESA study was approved by the Institutional Review Boards at all participating institutions, and all participants gave written informed consent. In addition, informed consent was obtained for extensive data sharing (dbGaP) and genetic/omic studies, including candidate genes (NHLBI CARe), genome-wide scans (NHLBI SHARe), exome sequencing (NHLBI ESP).

4.2 Metabolome Annotation

Metabolomic profiles for MESA samples were created by the Broad Institute using and liquid chromatography-mass spectrometry (LC-MS). Detailed experimental protocols have been reported elsewhere [39] [40] [41] [42] [43].

We processed the initial dataset of 6,042 detected metabolite LC-MS peaks. Initially, annotations of 492 ( 8.1%) were made using reference standards. To predict additional IDs, we employed MetID 44 , an R package specifically designed for metabolite identification. This tool utilizes accurate mass-to-charge ratios (m/z) and retention times (RT) to putatively identify unknown metabolites.

We leveraged seven publicly available databases: HMDB 45 , KEGG 46 , MassBank 47 , NIST, T3DB 48 , BloodExposome 49 , and DrugBank 50 . The best annotation match for each metabolite was retained based on the highest confidence from the available databases. As a result, out of the 5,962 initially unannotated metabolites, 5,938 (99.6%) were putatively annotated, representing a significant increase in coverage.

Of the original 6,052 detected metabolites, we putatively matched 3,085 unique compounds, suggesting a substantial level of duplication (2,856 metabolites, or 48.3%). This redundancy likely arises from mapping LC-MS peaks from isomeric compounds to a single database compound and the lack of retention time (RT) data in the databases used for mapping. Further, since RT is not considered in the matching process, multiple annotations could be assigned to the same metabolite LC-MS peak based solely on mass-to-charge ratios. A limitation to note is that RT varies greatly depending on the chromatic conditions, making retention times across different labs difficult to compare. Finally, while the three nontargeted LC-MS methods used to acquire the data employed different chromatography methods (hydrophilic interaction liquid chromatography (HILIC)-positive ion MS for polar metabolites, reversed phase C8 chromatography-positive ion MS for lipids, and reversed phase C18 chromatography-negative ion MS for compounds of intermediate polarity), there is overlapping coverage of subsets of metabolites. Thus, it is ultimately important to confirm identities of significant metabolite features using authentic reference standards.

4.3 Mapping Molecular Exposure Modules

To map the molecular exposome by using the metabolome and proteome as proxies, we used Weighted Gene Co-expression Network Analysis (WGCNA) 51 . WGCNA is a method aimed at building a biologically meaningful network to infer relationships between metabolites or proteins. In this context, "gene" co-expression networks can help us construct modules of co regulated metabolites/proteins and thus gives us biologically inferable modules of metabolites that act similarly. For example, if glucose and another carbohydrate are correlated, they should be in the same module.

One advantage of using WGCNA is that we do not need to specify the number of modules in advance, reducing bias. However, some bias remains, because researchers still indirectly choose parameters that affect the number and composition of the modules. We follow the pipeline summarized in Extended Data Fig. 6 to chose the parameters for WGCNA. For normalization, we explored both rank norm normalization and variance stabilizing transformation (VST). After examining the relationship between the rank of the mean values and the standard deviation (SD) of metabolites and proteins across both exams, we selected VST normalization as it effectively reduces variability across ranks, ensuring more consistent variance for downstream analyses. We adjusted for both ancestry PCs and batch effects. Specifically, we removed the first principal component, as well as ancestry PCs (Extended Data Fig. 7).

4.4 Annotating Molecular Exposure Modules

To characterize the metabolic MEMs, we performed over-representation analysis (ORA) against the Human Metabolome Database (HMDB) 45 , specifically chemical information found in the Classy-Fire fields, deciphering what chemical classes are enriched within each metabolic MEM. To ensure robust results, annotation terms were filtered to include only those containing between 3 and 500 metabolites. To characterize the proteomic MEMs, we performed ORA using the enrichR package 52 , specifically against Gene Ontology 53 , Reactome 54 , and KEGG 46 . Nominal p-values from both enrichment analyses, were separately adjusted for multiple testing using the Benjamini-Hochberg False Discovery Rate (FDR) method. A significant hit was defined as a hit with an F DR < 0.05.

4.7 Methylome and Transcriptome Pre-processing and Cell Type

De-convolution

Generally, we pre-processed the transcriptome and methylome of samples, we then deconvolved the bulk data into cell type specific data. In principle, this is similar to what was done previously 12.

• Transcriptome. To estimate the cell-type-specific gene expression profiles from the bulk MESA RNA-sequencing data, we utilized Tensor Composition Analysis (TCA) 55 . Specifically, we first took the bulk expression and normalized it to counts per million (CPM). To mitigate noise and focus on biologically relevant signals, we performed feature selection to identify highly variable genes (HVGs) using the scran R package 56 . We retained only the consensus HVGs that appeared in the top highly variable sets. Then, we took this bulk RNA-sequencing data, and using CIBER-SORT 57 we estimated the prevalence of each cell type using the default leukocyte reference matrix.

We then excluded cell types with less than a median of 0.1% proportion. Then, using the aforementioned proportions of each cell type, we utilized TCA to retrieve cell type specific expression profiles. Then, to enable downstream account for unobserved confounding variation (e.g. batch or population structure affects), we performed PCA, and approximated the optimal number of principal components as covariances by using the Gavish-Donoho method 58 . Transcriptomics were done on the PBMCs.

• Methylome. Generally, we followed a similar pipeline to the one we employed on the transcriptome. Specifically, we first pre-processed the data, then we estimated cell type proportions from the bulk methylation data, then we used TCA to de-convolve cell type specific individual methylome profiles. In particular, we first employed SeSame's 59 linear preprocessing pipeline using prepSesme "QGCDPIU". Wherein, raw IDAT data was processed by performing quality masking, background subtraction, dye-bias correction, and detection p-value masking. Then, to ensure we only used informative sites, we estimated per site its Median Absolute Deviation (MAD), retaining only probes with a M AD > 0.005. Afterwards, we used minfi's 60 "estimateCellCounts2" command together with FlowSorted.Blood.EPIC 61 reference dataset to estimate the cell type proportions from the bulk sample. We then normalized every sample to have its cell type proportion estimates sum to 1. We then employed TCA on the methylation betas to receive cell type de-convolved methylation profiles. To ensure each site is reliable within each of the cell type specific profiles, we again applied a M AD > 0.005 filter. To ensure the data maintains normality assumptions, we employed the RNOmni package 62 to rank-based inverse normal transform the probe data across samples. Then, similarly to what we did in the transcriptome pre-processing, we performed PCA, and approximated the optimal number of principal components as covariances by using the Gavish-Donoho method 58 . Methylomics were done on blood leukocytes.

4.11 Zero-Shot Cross-Cell-Type Prediction of G × E Interactions

To examine whether we could predict, using information we have in multiple cell types, whether a molecular phenotype (gene expression or methylation) will be affected by a G × E interaction, in a held-out cell type we developed a model. Specifically, using a leave-one-cell-type-out cross-validation (LOCTO) framework, we trained on G × E interaction data as well as appropriate molecular phenotype data from the remaining cell types and evaluated the performance on the left-out cell type in a zero-shot frame work, when cell type molecular phenotype is given. During prediction, the model has molecular phenotype data for the particular cell type in which it performs the G × E interaction prediction. With the expansion of next generation sequencing and the advent of single cell sequencing, most cell types are molecularly phenotyped 30, 67, 68 , thus, this prior information is readily available and applicable in zero-shot applications. The model used features from 3 sources: (1) cell-type-specific molecular phenotype features, (2) MEM specificity, and (3) features describing Gene's G × E interaction presence in other cell types.

All training-derived statistics were computed inside each fold without the left-out cell type to prevent data leakage from the held-out cell type into the trained model. Specifically, the variables used by the model were: "gene resp rank" which is calculated by ranking all the genes by the total number of MEMs with whom they are associated, and then dividing by the total number of genes, to get a percentile, "log module potency" which is calculated via the log1p of the total number of MEMs with whom the molecular phenotype is associated with, "gene n modules" which is calculated via calculating the number of unique MEMs with whom the molecular phenotype is associated, "module n genes" which is calculated via the number of unique molecular phenotypes associated with the MEM, "gene n cells" which is calculated via the count of distinct cell types in whom we see a G × E interaction with the same molecular phenotype, "expr x potency" which is calculated via an interaction term between log expr and log module potency, "log expr" which is calculated via a log1p of the de-convolution result, "is expressed" which is calculated via classifying above or below 0 of the raw de-convolution output, and "module n cells" which is calculated via the number of cell types in whom the MEM shows a G × E interaction affecting the levels of the molecular phenotype.

Classification was performed using XGBoosted trees 69 , we accounted for training class imbalance via inverse frequency weighting correction. The test cell type was never observed during training or model selection, preventing data leakage. we evaluated the models using the area under the precisionrecall curve (AUPRC) as our primary measurement. Given the high class imbalance, and AUPRCs dependence on prevalence, we reported the lift over the random baseline (AUPRC / prevalence).

4.12 Colocalizing Gene by Environment Interactions with Traits

To identify loci where G × E interactions may share a causal variant with a complex trait GWAS, we performed colocalization analysis following a similar approach to that used by Kasela et al 12 . Due to computational constraints, we restricted this analysis to G × E results from the first 18 metabolomic molecular exposure modules. In particular, we applied the coloc.abf method as implemented in the coloc R package 70 , restricting analyses to G × E loci where the lead interaction variant reached p int < 10 -5 . Variants within a 200 kb window of the lead interaction variant were clumped together to define each locus. We required a minimum of 50 variants overlapping between the G × E locus and the GWAS summary statistics per locus, to perform the colocalization analysis. The MHC region was excluded. Prior probabilities were set as p1 = 10 -4 , p2 = 10 -4 , and p12 = 5 × 10 -6 , and a posterior probability of a shared causal variant (P P.H 4 > 0.50) was used to define colocalization 12 . A subset of colocalized loci were additionally examined manually by visual inspection. The analysis utilized a set of harmonized and curated GWAS 20.
