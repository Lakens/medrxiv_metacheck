Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

It is possible that there is a true non-zero effect, but that the study did not detect it. Make sure your inference acknowledges that it is possible that there is a non-zero effect. It is correct to include the effect is ‘not significantly’ different, although this just restates that p > 0.05.

How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

This module was developed by Lisa DeBruine and Daniel Lakens

Read more in the metacheck manual.

Version 0.4.4.3 reported 419 p-values as imprecise, 388 of them correctly (93%), and missed 50 (89% found). How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

Deposits in archives for sequence and expression data (GEO, the INSDC archives BioProject, SRA, ENA and DDBJ, and ArrayExpress; see [seq_archive_links()]), mostly named by accession number, are read for whose deposit they are. The authors’ own are listed with what they hold ([seq_archive_size()]) and are not downloaded or checked as data and code; summary_table$archive_own_n counts them.

R packages on CRAN ([cran_links()], [cran_info()]) are the paper’s own when a paper author is a package author and the paper presents the package; the paper’s own are listed with their version and not checked (summary_table$cran_own_n). A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Abstract

Objective: Postpartum readmission is rare and costly, and risk tools often rely on routinely collected sociodemographic data. We asked what such data can support, whether algorithm choice matters, and when a modest model could pay for itself.

Methods: We analyzed 8,774 participants of the nuMoM2b cohort of first pregnancies, of whom 154 (1.8%) were readmitted within 14 days. Conventional, ensemble and automated machine learning models (FLAML, AutoGluon) were trained on 70% of participants, with every fitted step confined to training data, and evaluated once on the remaining 30% (46 readmissions). We compared models at default thresholds and equal screening workload, after recalibration, across richer feature sets, and in economic scenarios against contacting all or no patients.

Results: The best model, a tuned logistic regression, reached an area under the ROC curve (AUC) of 0.614 (95% confidence interval 0.542-0.685). Both automated frameworks discriminated worse (AUC 0.416-0.519) after optimistic internal validation. Sensitivity at the default threshold ranged from 0% to 41% and reflected classimbalance corrections rather than ranking ability; when every model flagged the same 28.4% of patients, conventional and ensemble models reached 11 to 20 of 46 readmissions. After recalibration, no model improved on predicting the base rate. Delivery and discharge information raised the AUC to 0.611-0.631, and learning curves were flat.

Reweighted post hoc to each US state's first births, the AUC ranged from 0.531 to 0.667, lowest in the least diverse states. Contacting everyone was optimal for low-cost outreach; near the break-even cost, no model gained more than its running cost.

Conclusions: Sociodemographic data alone cannot support a useful postpartum readmission tool, whatever the algorithm. Under class imbalance, default-threshold comparisons mislead. A modest model's value depends on the population and the intervention, which decision-economic analysis, not discrimination alone, should assess.

Future work should prioritize richer peripartum and postpartum data.

health 1 Introduction

Postpartum readmission represents a significant burden for new mothers, families, and healthcare systems, affecting approximately 1-2% of deliveries [1] and generating substantial inpatient costs. [2] Early identification of high-risk patients could enable targeted interventions to prevent readmissions, improve maternal outcomes, and reduce healthcare costs.

However, developing effective prediction models requires a careful balance between model performance, clinical interpretability, and implementation feasibility.

The emergence of automated machine learning (AutoML) has promised to democratize predictive modeling in healthcare by automating complex processes of algorithm selection, hyperparameter optimization, and feature engineering. [3, 4] Leading AutoML frameworks such as FLAML and TPOT claim to deliver superior performance while reducing the need for specialized machine learning expertise. This technological promise has generated significant interest in healthcare applications, where AutoML could accelerate the development and deployment of clinical prediction tools.

However, the clinical utility of AutoML in healthcare settings remains largely unproven, and systematic reviews note that healthcare-specific challenges-particularly class imbalance and the need for calibrated, interpretable outputs-are not yet well handled by generalpurpose AutoML systems. [5] Healthcare prediction models face unique challenges, including severe class imbalances, regulatory requirements for interpretability, computational resource constraints, and the critical importance of sensitivity over overall accuracy. [6, 7] Traditional machine learning approaches, particularly logistic regression, have demonstrated robust performance in clinical applications due to their interpretability, computational efficiency, and well-understood statistical properties. [8, 9] The nuMoM2b (Nulliparous Pregnancy Outcomes Study: Monitoring Mothers-to-be) cohort is one of the largest prospective cohorts of first pregnancies. [10] Routinely collected sociodemographic information is available for almost every participant, as it is in most delivery units, so it is the natural starting point for a readmission risk tool. Whether it is sufficient is a separate question. A rare outcome also exposes an under-appreciated problem in comparing algorithms: under severe class imbalance, a model's apparent sensitivity at the default 0.5 threshold depends on how resampling and class weighting shift its predicted probabilities, as much as on its ability to rank patients. [11] We therefore set out to establish what routinely collected sociodemographic data can and cannot support for predicting 14-day postpartum readmission. 2 Methods

2.1 Study Design, Data Source and Outcome

This is a secondary analysis of the nuMoM2b prospective cohort of nulliparous women with singleton pregnancies, recruited at eight US clinical sites. [10] The outcome was rehospitalization within 14 days of delivery (chart-abstraction item CMAJ01), and participants with this item recorded formed the analyzed cohort. The unit of analysis was the participant; each participant contributed one delivery and one row. Reporting follows TRIPOD guidance. [9]

2.2 Candidate Predictors and Leakage Control

We classified all 11,617 codebook variables by their timing relative to the outcome (Supplementary Table S1). Primary analyses used 18 sociodemographic and pre-pregnancy candidates: race and ethnicity (four codings), body mass index and its category, education, gravidity, three smoking items, five insurance-payer items, income relative to the federal poverty level and its category. Two preprocessing rules governed how items were coded.

First, items that are blank by design (cigarettes per day for participants who did not smoke in the three months before pregnancy; recent smoking for participants who had never used tobacco) were recoded as "none" rather than treated as missing. Second, unordered categorical items (race and ethnicity codings, marital status) were one-hot encoded, pooling categories with fewer than 20 participants, rather than entered as numeric codes.

Data were split once into training (70%) and test (30%) sets, stratified by outcome (seed 42); the code asserts that no participant appears in both. Every fitted step was learned on the training set or inside training folds and applied unchanged to the test set: imputation (median for numeric and ordinal items, mode for categorical items), standardization, recursive feature elimination (RFE; logistic-regression estimator, 10 features), SMOTE oversampling, [12] hyperparameter search, decision thresholds and recalibration. The test set was used once per model, for final evaluation.

2.3 Models

Original configuration. The configurations specified at the start of the study, with the preprocessing rules above, were logistic regression (L2, C = 1, balanced class weights), random forest (100 trees, balanced class weights) and gradient boosting (scikit-learn defaults), each with RFE and SMOTE inside the pipeline; logistic regression was also fitted without SMOTE.

Tuned models. Logistic regression, random forest and gradient boosting were tuned by randomized search (40 draws, stratified 5-fold cross-validation (CV) within the training set, ROC-AUC). The search treated the imbalance strategy as a hyperparameter: SMOTE or none, and balanced or no class weights (Supplementary Table S4).

Ensembles.

A stacking ensemble used the three base pipelines, with base-model probabilities from stratified 5-fold CV as inputs to a logistic-regression meta-learner (C = 1, balanced class weights). A soft-voting ensemble averaged the base models' probabilities after isotonic calibration, each by CalibratedClassifierCV with stratified 5-fold CV within the training set. Each ensemble was built from both the original-configuration and the tuned base models.

Automated machine learning. FLAML [3] was run as originally configured (SMOTEresampled training data, ROC-AUC, 300 s, default search space) and in an imbalance-aware configuration (original training data, balanced sample weights, 5-fold CV, ROC-AUC, 900 s).

AutoGluon-Tabular [13] was run with the best quality preset (bagging and multi-layer stacking, ROC-AUC, 900 s). Both frameworks received the same fold-fitted imputation, encoding and scaling as the other models. Because both searches are bounded by wall-clock time, their results can differ between runs; we report the first complete run and, in Results, a full rerun of the pipeline.

2.4 Operating Points

For every model, out-of-fold (OOF) predictions were obtained for the training set by stratified 5-fold CV of the final configuration. For AutoGluon, whose internal OOF estimates are inflated by selecting among many candidate models on the same folds, OOF predictions came from refitting AutoGluon within each outer training fold (300 s per fold). Decision thresholds were selected on these OOF predictions only and then applied to the test set.

They were the highest threshold reaching 80% and 70% OOF sensitivity, and the threshold flagging the same share of patients that the original-configuration logistic regression flagged at 0.5. This matched flag rate puts every model at an identical screening workload, so that their sensitivities can be compared directly. We also report each model at the default 0.5 threshold.

2.5 Calibration, Recalibration and Decision Curves

Calibration was summarized by the Brier score, the Brier score of a constant prediction equal to the training prevalence, and the calibration slope and intercept. For every model, Platt scaling (logistic regression on the logit of the OOF prediction) and isotonic regression were fitted to the training OOF predictions and applied to the test predictions. Decision curve analysis [14] compared the net benefit of recalibrated models with contacting all or no patients across threshold probabilities of 0.5-10%.

2.6 Statistical Analysis

Performance on the test set was summarized by ROC-AUC, PR-AUC (average precision; more informative under imbalance [15]), Brier score and operating-point sensitivity, specificity, positive predictive value and proportion flagged. 95% confidence intervals came from 1,000 bootstrap resamples, stratified by outcome. Paired AUC differences between the tuned logistic regression, pre-specified as the reference, and every other model were tested with De-Long's method, [16] with Holm correction across the 13 comparisons. As a chance-level control, the tuned logistic-regression configuration was refitted 200 times on randomly permuted training labels and evaluated on the test set.

2.7 Data-Limitation Analyses

To ask whether the limitation lay in the data rather than the algorithm, we fitted a learning curve for logistic regression (training subsamples of 20-100%, 5 × 5 repeated stratified CV within the training set). We also compared three nested feature sets with tuned logistic regression and gradient boosting (Supplementary Table S5). The first was the 18 sociodemographic candidates. The second added enrollment-interview items: age, marital status, asthma, number of pregnancies, tobacco history and preconception-counseling topics. The third added information available at delivery discharge: cesarean or operative vaginal deliv-ery, diabetes, treatment for depression or anxiety before or during pregnancy, preterm birth and small for gestational age. Each variable's timing was checked against the codebook.

Two hypertensive-disorder items (CMAE01, A09A03b) are recorded on the same chart abstraction as the outcome without a time window, so they may capture postpartum onset; they were excluded from the discharge set and examined only in a sensitivity analysis. These models used all variables with missing-value indicators, without RFE.

2.8 Post Hoc Search Over Variables Recorded Before Discharge

After the main results were known, we asked whether any information recorded in nuMoM2b before delivery discharge carried more signal than the pre-specified feature sets. Candidates were the codebook variables from the screening, enrollment, antenatal-visit, ultrasound and laboratory forms, together with the sections of the delivery chart abstraction covering admission, delivery, medications and laboratory results before discharge. Sections whose time windows could extend past discharge were excluded, as were items whose labels referred to dates, discharge, the postpartum period or readmission. Inside each training fit, variables with more than 50% missing values or a minority category below 0.5% were removed, as was any variable whose value or missingness alone predicted the outcome with a univariate ROC-AUC of 0.70 or more, as a guard against leakage. An L1-penalized logistic regression, with its penalty chosen by 5-fold cross-validation, was fitted to the remaining variables, and the stability of variable selection was estimated from 100 refits on random halves of the training set. The test set was scored once, and the model was compared with the tuned 18-variable logistic regression by DeLong's test and with 100 refits on permuted labels. This analysis was not pre-specified, and its design changed after test results had been seen: a first run was stopped after an antenatal-only variable set had been scored on the test set, and models with recursive feature elimination and the univariate leakage guard were then added.

2.9 Illustrative Economic Scenarios

We asked a narrower question than whether the model is cost-effective: at what cost of an outreach contact, if any, does acting on model-predicted risk outperform the two strategies that require no model, contacting every patient or contacting no one? Contacting a patient who would otherwise be readmitted yields an expected saving B = e × R, where R is the cost of a readmission and e the proportion of reached readmissions that the contact prevents. We applied this rule to Platt-recalibrated test-set risks (Section 2.5), so that c/B is a genuine risk threshold. Inputs and their sources are listed in Supplementary Table S2.

The base case used R = $8,100, the mean hospital cost of a postpartum readmission in the Nationwide Readmissions Database [17] inflated to 2024 dollars. We used the mean rather than the median because the expected value of a strategy depends on total cost, and readmission costs are right-skewed: the median cost of a readmission to the delivery hospital was $3,981 against a mean of $5,764 (2016 dollars). [17] Readmissions related to a hypertensive disorder of pregnancy, the condition behind the effectiveness evidence below, were not cheaper: in the same database for 2013-2014, the mean cost per woman of such readmissions within 42 days was $6,100-6,600 across hypertensive disorders (about $8,100-8,800 in 2024 dollars), and readmission costs were similar with and without a hypertensive disorder. [2] A post-discharge contact may nevertheless prevent mainly short readmissions, so as a lower bound we repeated the base case with R = $5,200, the same-hospital median inflated to 2024. It used e = 20%, close to the reductions in readmission reported for remote blood-pressure monitoring after hypertensive disorders of pregnancy (adjusted risk ratio 0.78) [18] and for transitional-care interventions in general (pooled risk ratio 0.82). [19] Effectiveness was varied over 10-50%. The upper value is optimistic: it is supported only by evidence rated low quality, [20] and a meta-analysis of randomized trials found no significant reduction. [21] Contact costs were varied from $5 to $400, a range that includes Medicaid payments for a home visit or a physician telephone call (national means $44 and $47 per claim line). [22] For each cost we report the model's gain over the better of the two nomodel strategies, per 1,000 deliveries, with a 95% interval from 1,000 bootstrap resamples of the test set. The model's running cost (annualized development, EHR integration and maintenance; $2,300-4,100 per 1,000 deliveries, Supplementary Table S2) is not included in that gain; we report it separately as the amount a gain would have to exceed. These scenarios are illustrative. They inherit every limitation of the underlying model and are not a cost-effectiveness analysis of a deployable tool.

2.10 Post Hoc Transport to State Birth Populations

This analysis was designed after the main results were known and is exploratory. The test set reflects eight academic centers, whereas the population in which a tool would be used differs from state to state in exactly the characteristics the model relies on. nuMoM2b records no state or site, so we reweighted the test participants to resemble each state's population of first births. Targets were the 2022-2024 distributions of singleton first births by state of residence from CDC WONDER natality data: [23] race and ethnicity (five groups), Medicaid versus other payer at delivery, education (six groups), pre-pregnancy body mass index category (five groups) and maternal age (four groups). These characteristics are recorded on both the nuMoM2b forms and the US birth certificate. Smoking was not used because the two sources define it differently. Weights were obtained by raking (iterative proportional fitting) and refitted within each of 300 bootstrap resamples of the test set. We report the weighted ROC-AUC of the tuned logistic regression's predictions, unchanged, and its Platt-recalibrated risks were used for the economics. States whose effective number of readmissions (Kish) fell below 11 were not reported. The transport assumes that the risk of readmission for a woman with given characteristics is the same in every state as in the nuMoM2b centers, so it captures differences in case mix but not in care.

For the economics, contact for women with government insurance was priced at the state's own Medicaid payment per claim line in 2022-2023 (T-MSIS Medicaid provider spending data; [22] national figure where a state had fewer than 1,000 lines), for an established-patient home visit (CPT 99347-99350) or a physician telephone call (99441-99443). Readmission cost was as in the base case, and effectiveness was 10%, 20% or 50%. Because commercial insurers pay more than Medicaid for both the contact and the readmission, women with other insurance were analyzed under three scenarios: Medicaid prices; commercial fee-for-service prices, with readmission cost multiplied by 2.55 and contact cost by 2.85 (commercial-to-Medicare price ratios of 2.55 for inpatient and 1.88 for professional services, [24] divided by a Medicaid-to-Medicare primary-care fee ratio of 0.66 [25]); and a salaried outreach program whose contact cost does not scale with commercial prices, with only readmission cost multiplied by 2.55. In each payer group the comparator was the better of contacting all or no women in that group. A model was judged to add demonstrable value in a state when the lower bound of the 95% interval of its gain exceeded zero; we report separately the cases in which the model flagged at least 95% of women, which amounts to contacting everyone.

All analyses were run from a single script (src/revision pipeline.py) in Python 3.11.13 with scikit-learn 1.6.1, imbalanced-learn 0.14.2, FLAML 2.7.0, AutoGluon 1.6.3 and statsmodels 0.15.0; the complete environment is listed in requirements-revision.txt. Every number in this paper is read from the files that script writes (results/revision/), and per-patient predictions are stored so that every metric can be recomputed. The economic scenarios, figures and tables are produced by separate scripts that read only those files. The code is publicly available on GitHub (release v1.0.1), [26] and an interactive explorer of the economic analyses, including the state-level analysis, is publicly available and archived on Zenodo. 3.2 Discrimination

Discrimination was modest for every model (Table 2, Figure 1). The tuned logistic regression had the highest test ROC-AUC, 0.614 (95% CI 0.542-0.685), and exceeded all 200 labelpermuted refits but one (permutation p = 0.010; permuted AUCs 0.381-0.609). Conventional and ensemble models ranged from 0.476 to 0.614. PR-AUC did not exceed 0.026 for any model, against a test prevalence of 0.017. Hyperparameter search selected neither SMOTE nor class weighting for any of the three conventional models.

Both AutoML frameworks discriminated worse than the tuned logistic regression: FLAML as originally configured 0.416 (0.334-0.494), FLAML imbalance-aware 0.461 (0.379-0.546) and AutoGluon 0.485 (0.400-0.567). These were the only differences that remained significant after Holm correction (DeLong p Holm = 0.003, 0.001 and 0.001); all other comparisons had p Holm ≥ 0.075. In a full rerun of the pipeline, every other model reproduced its test AUC exactly and AutoGluon to within 0.002 (0.483, p Holm < 0.001), but imbalance-aware FLAML reached 0.519 (0.444-0.598), and its difference from the tuned logistic regression was then not significant (p Holm = 0.21). Flexible models lost discrimination between training cross-validation and the test set, whereas the tuned logistic regression did not (0.602 in CV, 0.614 on test). The losses were 0.616 to 0.461 for imbalance-aware FLAML, 0.607 to 0.529 for the tuned random forest, 0.613 to 0.552 for tuned gradient boosting and 0.611 to 0.543 for stacking of the tuned models. AutoGluon's internal validation estimate (0.705) exceeded both its honest outer-fold estimate (0.589) and its test performance (0.485). FLAML as originally configured validated its search on a hold-out drawn from the SMOTE-resampled training data and reported an internal ROC-AUC of 0.999; the imbalance-aware configuration, validated by cross-validation on the original data, reported 0.694. and cross-validated training-set ROC-AUC (diamonds) for every model. Flexible models, and both AutoML frameworks in particular, lost discrimination between training and test; the tuned logistic regression did not.

3.3 Default Thresholds Versus Equal Workload

At the default 0.5 threshold, sensitivity ranged from 0% to 41.3% (Table 2, Figure 2), and the spread followed how each model was trained. Models whose final estimator was trained with SMOTE or class weighting flagged 10.3% to 36.3% of test patients. The exception was FLAML as originally configured, which flagged 1.9% and reached one readmission. The tuned conventional models, the soft-voting ensembles and AutoGluon produced probabilities near the base rate and flagged no one. Sensitivity at 0.5 therefore reflects the location of a model's probability scale, not its ability to rank patients.

When every model flagged the same 28.4% of test patients, sensitivity was much more uniform. Conventional and ensemble models reached 11 to 20 of 46 readmissions (23.9-43.5%), with widely overlapping intervals, and the three AutoML configurations reached 9 to 12 (19.6-26.1%). Positive predictive value was 1.2-2.7% at this workload. Thresholds chosen to flag the same proportion of training patients did not equalize workload on the test set: the share of test patients flagged ranged from 20.9% to 59.4%, because final models and out-of-fold models produced differently distributed scores. We therefore matched workload directly on the test score distribution, which uses no outcome information.

Thresholds selected on training data to reach 80% out-of-fold sensitivity achieved 58.7% test sensitivity for the tuned logistic regression, flagging 45.0% of patients. For the logistic regression as originally configured they achieved 76.1%, flagging 67.4%. Per 1,000 deliveries, the tuned model at this threshold would flag 450 women to reach 10 of the 17-18 who would be readmitted (number needed to screen 44).

3.4 Calibration and Decision Curves

The logistic regression as originally configured, trained with SMOTE and class weighting, greatly overestimated risk (Figure 3a). Its Brier score was 0.2267, against 0.0172 for a constant base-rate prediction, with a calibration slope of 0.34 and intercept of -4.04. The tuned logistic regression was close to calibrated (Brier 0.0171, slope 0.89). After Platt recalibration every model's Brier score was 0.0172, and after isotonic recalibration 0.0172-0.0174: no model predicted readmission better than assigning every patient the base rate.

In decision curve analysis (Figure 3b), the largest net-benefit gain of any recalibrated model over the better of contacting all or no patients was 0.0022, or about two net true positives per 1,000 deliveries (tuned logistic regression).

3.5 Data Limitation

The pre-specified learning curve (logistic regression with RFE) stayed between 0.508 and 0.539 across training sizes (Figure 4a). This curve fell well below the same data modeled without RFE, so we added a post hoc curve for the tuned logistic regression using all 18 variables. It rose from 0.594 with 982 training participants to 0.622 with 1,964 and then remained flat (0.621-0.624), indicating that more participants with the same variables would not improve discrimination. Adding enrollment-interview items did not improve test discrimination (Table 3, Figure 4b). Adding delivery and discharge information raised test ROC-AUC to 0.611 (0.532-0.690) for logistic regression and 0.631 (0.547-0.709) for gradient boosting, with PR-AUC up to 0.034. Including the two untimed hypertensive-disorder items changed these values little (0.625 and 0.627). No feature set reached a ROC-AUC of 0.70.

In the post hoc search over variables recorded before discharge (Section 2.8), 1,370 of 4,887 candidates passed screening in the training set, and the L1-penalized model retained 110 non-zero coefficients. Its test ROC-AUC was 0.663 (95% CI 0.580-0.734; cross-validated 0.677). A full rerun of the same code reproduced these values to three decimals and selected the same twelve stable variables, but retained 113 coefficients and shifted individual selection frequencies by up to 0.03, because the L1 solver was run without a fixed random seed. This exceeded every label-permuted refit (permutation p = 0.010) but was not significantly higher than the tuned 18-variable model (difference 0.049, DeLong p = 0.24). Twelve variables were selected in at least half of the stability refits (Supplementary Table S6). They described the delivery admission and course (admission for a maternal medical or obstetric condition, cesarean delivery, other medications and prophylactic antibiotics), a history of cervical surgery, a uterine artery Doppler index, waist circumference, pre-pregnancy binge drinking, preconception counseling and tiredness in mid-pregnancy. None of the 18 sociodemographic variables, all of which were candidates, was among the 30 most frequently selected.

With 108 training events, a model with 110 coefficients is heavily over-parameterized, and only two variables were selected in more than 80% of refits, so we treat the selected variables as hypotheses rather than as a model.

Reweighting was possible for every state, and 50 jurisdictions (49 states and the District of Columbia) had enough effective readmissions to report; West Virginia was suppressed (10.2 effective readmissions). 4 Discussion

4.1 Principal Findings

Routinely collected sociodemographic data supported only modest discrimination of 14-day postpartum readmission in this cohort of first pregnancies. The best model reached a test ROC-AUC of 0.614, and no feature set exceeded 0.631. After recalibration, no model predicted readmission better than assigning every patient the base rate, and decision curves showed no meaningful net benefit over contacting all or no patients. When models were compared at an equal screening workload, conventional and ensemble approaches were indistinguishable. Both AutoML frameworks discriminated worse, because the configurations they selected did not hold up on the test set. A model's high sensitivity at the default threshold, set against the near-zero sensitivity of others, can look like greater clinical utility; here that contrast came from how each model's probabilities were scaled.

4.2 Default Thresholds Mislead Under Class Imbalance

At the default 0.5 threshold, sensitivity ranged from zero to over 40%, and the spread was explained by whether a model had been trained with SMOTE or class weights. Both shift predicted probabilities upwards, so that 0.5 falls inside the bulk of the score distribution instead of far above it. A calibrated model of a 1.8%-prevalence outcome will rarely predict 50% for anyone, and will therefore appear to "collapse to the majority class" at that threshold whatever its ranking ability. The same imbalance corrections that produce apparent sensitivity also destroy calibration, as van den Goorbergh and colleagues showed for logistic regression. [11] In our data, the corrected model's Brier score was more than ten times that of a constant prediction. Comparisons between algorithms under imbalance should therefore be made at an equal workload or across thresholds, never at the default, and probabilities intended for decisions should be recalibrated. Thresholds must also be chosen without the test set. Thresholds tuned on the test data are optimistic. Selected on training data, the threshold aimed at 80% sensitivity reached 58.7% to 76.1% on the test set, depending on the model, and required flagging 45-67% of patients.

4.3 Why the AutoML Frameworks Did Worse Here

With 108 training events, cross-validated estimates of discrimination are noisy, with SDs of about 0.04-0.07 in our learning curves. A search over many flexible configurations then tends to select the one whose noise happened to be favorable. AutoGluon illustrates this most clearly. Its internal estimate of 0.705 came from choosing among about 100 candidate models and fitting ensemble weights on the same out-of-fold predictions; refitting it inside outer folds gave 0.589, and the test set gave 0.485. The tuned random forest, gradient boosting and stacked ensembles showed smaller versions of the same drop, whereas the heavily regularized logistic regression did not. For FLAML as originally configured, the optimism had a second, avoidable source: oversampling the training data before the search placed synthetic readmissions interpolated from the same patients on both sides of its internal validation split, giving an internal ROC-AUC of 0.999 against 0.416 on the test set. Resampling must be applied inside each training fold only. Our conclusions concern FLAML and Auto-Gluon under the configurations and time budgets we tested, at this event count. They do not imply that AutoML is unsuitable for clinical prediction in general. They do show that, for rare outcomes, an AutoML framework's internal validation score should not be taken at face value, and that nested or outer-fold validation is needed before its output is trusted.

4.4 What Data Would Be Needed

Two observations indicate that the limitation lies in the information available rather than in the algorithm or the sample size. First, once all 18 sociodemographic variables were used, the learning curve flattened from about 2,000 training participants onwards, so a larger co-hort with the same variables would be unlikely to help. Second, every algorithm, tuned or not, converged on similar modest discrimination, and adding enrollment-interview items changed nothing. Information available at delivery discharge (mode of delivery, preterm birth, growth restriction and mental-health treatment) raised discrimination modestly, to 0.611-0.631.

In the cohort table, readmission rates were highest after cesarean delivery and with a recorded hypertensive disorder. This points to the peripartum and early postpartum course as the most promising source of signal. A post hoc search over all variables recorded before discharge pointed the same way. Its most stable predictors described the delivery admission and course, vascular and body-size measures and mood in pregnancy, and none was sociodemographic, but even this search did not improve significantly on the 18 sociodemographic variables (0.663 against 0.614). Candidate data include blood pressure trajectories and antihypertensive treatment at discharge, delivery complications and their management, length of stay, discharge laboratory values, and the social and logistical circumstances of the first postpartum week. Many of these are not captured in research cohorts designed around pregnancy outcomes. Hypertensive-disorder items whose timing could not be verified added little in our sensitivity analysis. Any future model will need the same explicit check that predictors are fixed before discharge, because postpartum hypertension is both a predictor and a cause of readmission.

4.5 Implications for Clinical Implementation

A screening tool built on these data would place a heavy and unproductive load on postpartum services. At an operating point aimed at capturing most readmissions, the tuned model would flag 450 of every 1,000 delivering women in order to reach about 10 of the 17-18 who would be readmitted, a number needed to screen of 44. Even at the more selective workload of 28.4%, 37 women would need to be contacted per readmission reached. Flagging close to half of a delivery population defeats the purpose of selective risk stratification, which is to concentrate scarce nursing and care-coordination time. The same arithmetic applies per flagged patient. Contacting a flagged group is worth its cost only if the proportion of that group who would otherwise be readmitted, the positive predictive value, is at least c/B. At the Medicaid payment for a home visit ($44) and the base-case value of $1,620 per reached readmission, that is 2.7%; at the 28.4% workload, positive predictive value was 1.2-2.7%.

It also invites alert fatigue: when nearly every second discharge is flagged, staff learn to disregard the flag, including in the minority of cases where it is right. Because the strongest signals were social and economic (education, payer, smoking), flags would fall disproportionately on women already exposed to structural disadvantage. Without an intervention that demonstrably helps them, this risks stigmatization without benefit. Finally, probabilities from a model of a rare outcome must be recalibrated to the local population, and thresholds set and periodically reviewed by each site. That governance has a cost, and our economic scenarios suggest it would not be recovered at this level of discrimination.

Where a modest model could earn its keep. The economic analysis reframes the question of whether a weak model is "worth it". The answer depends less on the model's AUC than on where the intervention's cost places the decision threshold relative to prevalence.

When contact is cheap, contacting everyone is optimal and a screening model can only lose readmissions that it fails to flag. When contact is expensive, few patients have predicted risks high enough to justify it. Any model has room to help only near the cost at which the two no-model strategies break even, prevalence multiplied by the value of reaching one readmission. That window is narrow, and it moves with assumed intervention effectiveness (Figure 5). With a readmission cost taken from national data and effectiveness taken from the published evidence, no model in our study established a gain within this window that exceeded its own running cost.

The closest, a stacking ensemble whose discrimination did not exceed chance, came near it only at the optimistic 50% effectiveness. The real prices of outreach sharpen the point: what Medicaid pays for a home visit or a telephone call lies above the base-case break-even cost, so even contacting everyone would not pay unless the intervention works better than the evidence shows. The lesson is nevertheless general. Models with modest discrimination are routinely discarded on their AUC, yet whether a model has value depends on the intervention it would trigger. A model's gain comes from how well it separates patients on either side of the decision threshold, which no discrimination metric captures, and the window in which this matters moves with the cost and effectiveness of the intervention. This logic applies to any rare, costly outcome. Before a risk model is built or discarded, the intended intervention's cost and effectiveness should be used to locate this window, and candidate models should be evaluated within it. A better model would widen it.

Population and payer shape a model's value. The post hoc transport to state birth populations adds a further caution. The same model, with unchanged coefficients, discriminated close to chance when the test set was reweighted to states where most first births are to non-Hispanic White women, and best when it was reweighted to more diverse states. Its signal comes from sociodemographic differences, and these vary more in some populations than in others. Its economic value moved with the case mix, the payer mix and the price of contact, and no state showed a demonstrable gain across scenarios. A model's value is therefore a property of the model, the population and the intervention together, and an estimate from a single cohort, ours included, cannot show where deployment would pay.

We present the state results as a demonstration of this dependence, not as a recommendation for or against any state. The dependence also has an equity side: a tool that discriminates mainly through race, ethnicity and payer performs best where these differences are largest, which is also where the risk of stigmatizing flags described above is greatest.

4.6 Comparison with Prior Work

Our findings agree with a systematic review that found no consistent performance advantage of machine learning over logistic regression for clinical prediction models, [8] and with simulation evidence that class-imbalance corrections harm the calibration of risk models. [11] They also extend a previous analysis of the same cohort, which identified demographic and socioeconomic factors associated with postpartum rehospitalization. [28] Associations of this kind can be real, as in our cohort table, without supporting useful individual prediction.

4.7 Limitations

Few events. The test set contained 46 readmissions, so every interval is wide, and single readmissions move sensitivity by more than two percentage points. We present all model variants and their intervals rather than a single best model.

Analyst choices made after results were seen. Five analyses were added after earlier results were available, and we label each where it is reported: the equal-workload comparison on the test score distribution, adopted after training-quantile thresholds failed to equalize workload; the learning curve without RFE; the search over variables recorded before discharge, whose design changed after test results for an antenatal variable set had been seen; the transport to state birth populations; and the two preprocessing rules (structural missingness and coding of unordered categories), adopted after earlier results had been seen.

They changed individual estimates but not the conclusions.

Thresholds. All decision thresholds were selected on training data, but they were evaluated in a single test set and would need re-estimation at any site that adopted them.

Economic inputs.

The economic conclusions are only as good as their inputs, and the weakest is intervention effectiveness. No trial has tested whether a post-discharge contact prevents all-cause readmission in an unselected postpartum population. The evidence we used comes from remote blood-pressure monitoring after hypertensive disorders of pregnancy, from an observational cohort and from trials that disagree, [18, 20, 21] and from transitional- so results for such states rest on few participants. Rurality, which is not available in the data we analyzed, could not be adjusted for at all. Every state reuses the same 2,633 participants and 46 readmissions, so the state results are a sensitivity analysis, not independent state estimates. Commercial prices were scaled from national ratios rather than state-specific data.

Single cohort and outcome definition. nuMoM2b enrolled nulliparous women at academic centers, and readmission was abstracted from charts at the delivery hospital, so readmissions elsewhere may have been missed. Results may not transfer to multiparous or community-hospital populations.

AutoML scope. We evaluated two frameworks under specific configurations and time budgets. Other frameworks, longer searches or custom objectives might behave differently.

4.8 Future Directions

Prediction of postpartum readmission should be attempted with data on the delivery hospitalization and early postpartum period, collected with explicit timestamps relative to dis-charge, and evaluated with recalibration, equal-workload comparisons and decision analysis rather than discrimination alone. Because the evidence that post-discharge contact prevents readmission comes almost entirely from remote blood-pressure monitoring after hypertensive disorders of pregnancy, [18, 20, 21] a more promising design pairs a cause-specific outcome with an intervention known to act on it, for example hypertension-related readmission with remote blood-pressure monitoring, rather than all-cause readmission with an unstructured telephone call. The economic window described here can be used before model development, with that intervention's cost and effectiveness, to decide whether a model is worth building at all.

5 Conclusions

Routinely collected sociodemographic data cannot support a useful tool for predicting 14-day postpartum readmission after a first birth, whatever the algorithm. The best model reached a ROC-AUC of 0.614 and, once recalibrated, offered no net benefit over contacting all or no patients. Apparent differences between algorithms at the default threshold reflected how class-imbalance corrections scale predicted probabilities, not differences in ranking ability.

Two AutoML frameworks discriminated worse than a regularized logistic regression because their internal validation was optimistic at this event count. Delivery and discharge information added a little signal, and the learning curve was flat, so future work should prioritize richer peripartum and postpartum data over larger samples of the same variables. Whether any model is worth deploying depends on the cost and effectiveness of the intervention it would trigger, and on the population: for cheap outreach, contacting everyone is the better policy, and only within a narrow cost range can a weakly discriminating model add value.

In our data no model recovered its running cost there, and discrimination varied with the population to which the model was applied. Decision-economic evaluation in the intended population should therefore precede the decision to build, deploy or discard a modest model.

With a contact cost

c, the rational policy contacts a patient when her predicted risk is at least c/B, and the value of any strategy per patient is B • TP/n -c • (TP + FP)/n. This is decision curve analysis expressed in monetary units. [14] Contacting everyone and contacting no one have equal value when c equals prevalence × B. A model can add value only when its predicted risks separate patients on either side of c/B, so this is the cost at which any model has the most room to help.
