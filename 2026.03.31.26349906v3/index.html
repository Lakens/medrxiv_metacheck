This module uses regular expressions to identify sentences that contain a statistical power analysis. The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). When the sentence of a test says it is one-sided (“one-tailed”, “one-sided” or “directional”), a p-value that fits a one-sided test counts as consistent (statcheck’s OneTailedTxt setting; #695). When the paper says anywhere that its tests are one-sided, a p-value that fits a one-sided test in either direction counts as consistent too: half the two-sided p, or 1 minus that half for an effect against the predicted direction. Equivalence tests (TOST) are left out, as their p-values do not test the difference. A statistic written with “<” or “>” is read as a bound, and in a sentence about equal variances an F-test’s two-sided p (twice the one-tailed p) counts as consistent. For more information, see StatCheck.

This module only checks statistical results reported in the running text of the manuscript. It cannot (yet) process statistics reported only in tables.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Codebook Check works

This module checks whether the data columns in a repository are documented in a codebook or README. It locates codebook/readme files, extracts the variable definitions they contain, matches those definitions against the data columns extracted by data_check, and reports documentation coverage: how many data columns are documented, and which documented variables are never used.

The Codebook Check module consumes the columns and file classification produced by data_check (and, transitively, repo_check). Files classified as codebook or readme are parsed with parse_codebook(), which reads structured tables (CSV/TSV/Excel with a variable-name column and a label column), embedded labels in haven files (SPSS/Stata/SAS), and plain text from rich-text formats (docx/pdf/rtf/odt). The module defaults to rules-only when llm_use(FALSE). How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A link to a file-sharing service (Google Drive, Dropbox, OneDrive, Box, WeTransfer, MEGA, iCloud Drive, Baidu Netdisk, SURFdrive; see [file_share_links()]) gets a warning and makes the light yellow: such services are not repositories, as files can be changed or deleted at any time, get no DOI, and the link stops working when the account is closed. The report advises a stable repository such as Zenodo instead. Their files are not read, and summary_table$file_share_n counts the links.

Deposits in archives for sequence and expression data (GEO, the INSDC archives BioProject, SRA, ENA and DDBJ, and ArrayExpress; see [seq_archive_links()]), mostly named by accession number, are read for whose deposit they are. The authors’ own are listed with what they hold ([seq_archive_size()]) and are not downloaded or checked as data and code; summary_table$archive_own_n counts them.

R packages on CRAN ([cran_links()], [cran_info()]) are the paper’s own when a paper author is a package author and the paper presents the package; the paper’s own are listed with their version and not checked (summary_table$cran_own_n). A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. When every linked deposit is set aside, the traffic light is “na”. A deposit that is the paper’s own is counted as such when its README, title or description names the paper (its title or DOI).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. Abstract

Objectives Publicly available datasets for clinical speech de-identification remain scarce due to privacy constraints and annotation complexity. We address this gap with the 2025 SREDH/AI Cup SHI Speech Corpus, a time-aligned clinical speech dataset for detecting sensitive health information (SHI).

The dataset integrates three sources: the OpenDeID-v2 corpus, the dataset for automated medical transcription and medical dialogues derived from Taiwanese television dramas, combining English medical speech with Mandarin Chinese utterances. All audio was manually annotated with millisecond-level, time-aligned SHI segments using a schema of eight primary categories and 38 subcategories of which 26 were attested.

The corpus comprises approximately 20 hours of annotated audio (19.36 hours English, 0.89 hours Chinese) and 7830 SHI entities, split into training (10 hours, 1539 files), validation (5 hours, 775 files) and test (5 hours, 710 files) sets, supporting evaluation of both automatic speech recognition (ASR) and SHI recognition. Interannotator agreement (Fleiss's kappa) reached 0.907. In the 2025 SREDH/AI Cup competition, top-performing systems achieved a mixed error rate of 0.1147 in ASR and a macro F1 of 0.7103 in SHI recognition.

Discussion SHI category distribution is long-tailed, and English-Chinese data volume is highly imbalanced, underscoring the scarcity of Chinese clinical speech resources and the difficulty of time-aligned annotation in low-resource settings.

This corpus approximates dialogue-based clinical scenarios and supports research on medical speech de-identification, offering a unique reference for lowresource clinical speech privacy protection.

Key message

What is already known on this topic -Publicly available clinical speech datasets containing time-aligned sensitive health information (SHI) annotations for clinical speech de-identification research are limited. What this study adds -The 2025 SREDH AI Cup SHI Speech Corpus introduces a clinically oriented speech dataset with millisecond-level time-aligned SHI annotations covering 26 of the 38 SHI subcategories defined in the annotation schema. -The corpus integrates structured annotation protocols and standardized data processing to support the reproducible benchmarking of speech-based deidentification models. How this study might affect research, practice or policy -The availability of time-aligned SHI annotations may facilitate research on real-time or streaming de-identification systems beyond conventional, transcription-focused approaches. -This dataset may support the development of privacy-preserving technologies for clinical speech in bilingual settings involving English and low-resource languages.

INTRODUCTION

Clinical data contains a wealth of information valuable for researchhttps://ieeexplore.ieee.org/document/9039685 1, 2 and to prevent the leakage of private information, sensitive health information (SHI) must be removed or replaced with the corresponding surrogates before such data can be used. The 2014 i2b2 https://www.sciencedirect.com/science/article/pii/S1532046415001823?via%3Dihub clinical de-identification natural language processing challenge released a corpus of 1304 medical records from 296 patients with diabetes. These records contain detailed clinical narratives annotated for SHI. The MIMIC-III de-identification dataset 4 comprises 60 725 manually annotated SHI entities, categorised into six major classes and 22 specific types.

In addition, the OpenDeID-v2 5, 6 corpus, released during the 2023 SREDH/AI Cup competition, was constructed from 3244 electronic medical records and includes annotations for SHI and temporal normalisation. Although these resources are well suited for training a named entity recognition (NER) model for the de-identification task, they are text-based and therefore cannot be directly applied to speech de-identification.

Existing speech corpora like LibriSpeechhttps://informatics.bmj.com/content/33/https://informatics.bmj.com/content/33/1/e102158#ref-9/e102158#ref-7 7 Common Voicehttps://informatics.bmj.com/content/33/1/e102158#ref-8 8 AISHELL-1 9 and MagicData-RAMC 10 are predominantly compiled for automatic speech recognition (ASR) rather than de-identification. SLURP https://informatics.bmj.com/content/33/1/e102158#ref-11 is a 58-hour English speech dataset spanning 18 domains, 46 intents and 54 entity types, including person and datetime information. AISHELL-NER 12 extends the AISHELL-1 corpus by annotating three common entity types: names, organisations and locations. Nevertheless, these datasets are primarily designed for general-domain spoken language understanding, and their linguistic coverage does not align well with the characteristics of clinical communication. More importantly, their annotations are entity-centric rather than temporally grounded, lacking information about where each entity occurs in the speech signal. Therefore, a key gap in existing research is the lack of timestamp-level entity annotations for clinical speech. 12 To address this gap, we compiled the 2025 Secure Research Environment for Digital Health (SREDH)/AI Cup SHI Speech Corpus as a domain-specific evaluation resource for speech de-identification. This corpus is primarily designed as an English clinical speech benchmark, with a smaller Mandarin Chinese subset as a supplementary bilingual extension. Its content simulates dialogue-based clinical scenarios, and all recordings are accompanied by human-verified transcripts and time-aligned annotations covering 26 of the 38 SHI subcategories defined in the annotation schema. This design supports Englishcentric evaluation while providing an initial basis for future research on bilingual and codemixed clinical speech de-identification.

METHODS

Data source

The 2025 SREDH/AI Cup SHI Speech Corpus was constructed by integrating and extending complementary medical-domain resources from the OpenDeID-v2 corpushttps://informatics.bmj.com/content/33/1/e102158#ref-6 6 the dataset for automated medical transcription (DAMT) 13 and clinical-style dialogue materials from licensed videos from Taiwanese television dramas provided by Taiwan Public Television Services (PTS).

The OpenDeID-v2 corpus was originally released for the 2023 SREDH/AI Cup 6 . It comprised unstructured electronic medical record (EMR) reports derived from Australian hospitals 14.

While this corpus provides comprehensive text-level SHI annotations, it lacks corresponding speech recordings. In contrast, DAMT contains high-quality psychiatric dialogue recordings generated from scripted clinical scenarios. However, it lacks explicit SHI entity annotations necessary for structured de-identification modelling.

Given that both datasets were English-only, we incorporated clinical-style Chineseoriented dialogue audios from PTS to enhance linguistic diversity and real-world applicability. The resulting bilingual dataset, which combines English-dominant resources with Mandarin Chinese data, better reflects authentic clinical communication patterns observed in Taiwanese healthcare contexts. By integrating these three data sources, we established a unified dataset containing audio recordings with temporally aligned SHI annotations.

However, as the corpus does not include corresponding speech recordings, the text reports were converted into spoken-language scripts to enable natural speech-based modelling. A subset of 300 EMR reports was randomly sampled and rephrased into recording scripts by two domain specialists. During this process, the original surrogated SHI annotations were strictly preserved to maintain annotation consistency. Each script, approximately 100-200 words in length, was adapted to simulate natural clinical discourse while retaining the original entity structure.

The prepared scripts were recorded by 25 participants (9 males and 16 females), each contributing 10-20 audio samples. To ensure interspeaker consistency, all participants rehearsed their assigned scripts independently and received standardised instructions regarding speech rate, pause placement and pronunciation. Data acquisition took place in quiet, enclosed environments, with all samples captured using smartphone devices.

For the 2025 SREDH/AI Cup competition, the compiled corpus was partitioned into training, validation and test sets according to the data source and intended evaluation scenario. For the PTS-derived Chinese audio, the selected clinical dialogue segments were randomly split by duration into training and test sets using a 1:1 ratio, respectively. The split was performed at the segment level after non-clinical content, background audio and unrelated scenes were excluded.

For the English data, the test set was designed to reflect the target application scenario of speech de-identification from clinical-style spoken content. Accordingly, the English test set consisted only of self-recorded audio generated from rephrased OpenDeID-v2 corpus reports, whereas DAMT recordings were excluded from the English test set and used only for training and validation. This source-aware design reduced potential overlap between training and test scripts and mitigated the risk of information leakage, given that DAMT is publicly available and its reference transcriptions could potentially be accessed by participants in advance. The resulting partition enabled separate evaluation of transcription performance and temporally aligned SHI recognition under a setting closer to the intended use case.

RESULTS

The 2025 SREDH/AI Cup SHI Speech Corpus comprises approximately 20 hours of audio (20.25 hours in total), including DAMT (59%), OpenDeID-v2 corpus (36%) and PTS-based scripted clinical dialogues (5%). This composition yields 19.36 hours of English and 0.89 hours of Chinese speech. Please note all percentages are rounded to the nearest integer and durations to two decimal places; rounded figures may therefore not sum exactly to the stated totals. The corpus was partitioned into training, validation and test sets of approximately 10, 5 and 5 hours, respectively. The English corpora used in this study exhibit distinct accent characteristics based on their sources. While the DAMT dataset lacks explicit linguistic labelling, it is presumed to predominantly feature American English; conversely, the English audio in OpenDeID-v2 corpus primarily consists of Taiwanese English accents. Regarding the Chinese corpora, all recordings consistently feature Taiwanese Mandarin. All subsets maintained a signal-to-noise ratio (SNR) above 28 dB, indicating sufficient acoustic clarity for downstream processing. Speech rate across the three data sources was quantified using syllables per second (SPS). Statistical analysis revealed that the mean SPS for all three sources consistently ranged between 3.233 and 3.867, indicating a highly comparable speaking pace across the datasets. Furthermore, univariate analysis of the SPS metric demonstrated distinct patterns in data dispersion: the SD of SPS for both English sources was close to 1.0, aligning with a standard distribution. In contrast, the Chinese dataset exhibited a substantially larger SD, a finding that reflects the pronounced variability introduced by collecting Chinese speech samples from diverse dramatic sources. Detailed file counts and SNR statistics for each subset are provided in table 2. Given the fine-grained and temporally localised nature of SHI annotation in audio, maintaining annotation consistency was essential to ensure dataset reliability. After 12 iterative calibration rounds, the annotation team achieved a Fleiss's Kappa of 0.907. Following these protocols, 7830 SHI entities across 26 subcategories were annotated across the 20-hour corpus for the SHI recognition task. Several entity categories occurred at very low frequencies, resulting in a pronounced long-tail distribution, as illustrated in table 3. This corpus was adopted as the benchmark dataset for the 2025 SREDH/AI Cup Medical Speech Sensitive Information Recognition Competitionhttps://informatics.bmj.com/content/33/1/e102158#ref-19 [19] [20] [21] which aimed to evaluate state-of-the-art systems for ASR and SHI recognition in clinical speech. The challenge was organised into two sequentially linked subtasks, each targeting a distinct capability required for speech-based de-identification. The ASR subtask required systems to produce faithful transcriptions of clinical dialogues, whereas the SHI recognition subtask required systems to detect, temporally localise and classify SHI mentions from the spoken input. The top-performing team 22 adopted a dual-modality pipeline approach. For the ASR subtask, they fully fine-tuned CrisperWhisper 23 and FireRedASR 24 as the English and Chinese ASR models respectively. For the SHI recognition subtaskhttps://informatics.bmj.com/content/33/1/e102158#ref-26 they used Qwen3 25 as the backbone and applied NEFTune, 26 which injects random noise into the input embeddings during fine-tuning to improve generalisation. https://informatics.bmj.com/content/33/1/e102158#DC1 S2 summarises the final results of the top five teams. Whisper was the most widely adopted model for the ASR subtask, whereas the SHI recognition methods diverged into two contrasting paradigms: generative approaches, represented by Qwen 3 and Llama 3, and semantic-understanding approaches based on BERT-style encoders such as DeBERTa and RoBERTa. Across the benchmark, the rank-2 team achieved the best mixed error rate (MER) of 0.1147 in the ASR subtask, while the rank-1 team achieved the highest macro F1-score of 0.7103 in the SHI recognition subtask. In contrast, the average performance across participating systems was considerably lower, with an MER of 0.3539 and a macro F1 of 0.2696. The discrepancy between leading and average systems underscores the complexity of the task, especially when moving beyond transcription toward temporally aligned recognition of clinically sensitive entities. These results demonstrate that the 2025 SREDH/AI Cup SHI Speech Corpus serves not only as a shared evaluation resource but also as a challenging benchmark for developing robust, clinically grounded and clinical speech de-identification methods under the English and low-resource bilingual conditions.

DISCUSSION

The 2025 SREDH/AI Cup SHI Speech Corpus was developed to address two important gaps in existing resources: the limited availability of speech data for deidentification research and the lack of temporally aligned SHI annotations in clinical speech datasets. Because clinical speech data suitable for de-identification research remains critically scarce, we constructed a controlled clinical-style speech corpus by reformulating OpenDeID-v2 corpus reports into spoken-language scripts, incorporating existing clinical-style dialogue recordings and adding selected Chinese dialogue materials. The resulting corpus provides audio recordings with human-verified transcripts and time-aligned SHI annotations, thereby supporting the development and evaluation of speech-based de-identification methods.

Certain categories of SHI appear far less frequently than others, forming a long-tail pattern. This pattern is not incidental; rather, it reflects both the properties of the source materials and the distributional characteristics commonly observed in clinical documentation. For examplehttps://informatics.bmj.com/content/33/1/e102158#ref-14 CONTACT entities appear sparsely, consistent with the previous study, 14 which noted that clinical records carry limited patient-related attributes such as occupation or contact information. Based on our observations, the DAMT data contains almost no IDrelated entities. Prior work 27 has similarly shown that publicly available de-identification datasets tend to overrepresent common SHIs such as names, while underrepresenting less frequent categories such as passport numbers and identification numbers. This imbalance has important implications for model development and evaluation, as performance on common SHI categories may not fully reflect a system's ability to recognise rare but privacy-critical entities.

Beyond the distribution of SHI categories, the corpus is also shaped by its linguistic composition. The corpus was developed primarily as an English-dominant evaluation resource, with Chinese data included as an extension motivated by the prevalence of bilingual communication in certain clinical settings. 28 Despite this motivation, the dataset is heavily skewed toward English, reflecting the broader scarcity of annotated Chinese clinical speech resources. The compilation process itself illustrates this scarcity. Although audio from Chinese films and dramas is abundant, most candidate materials were not suitable for inclusion. As Tannen observes in her book Talking Voiceshttps://informatics.bmj.com/content/33/1/e102158#ref-29 29 dramatic dialogue is a distilled and refined version of reality rather than a direct imitation of everyday interaction, and personal identifiers are often deliberately omitted to preserve narrative flow. After applying SHI-compliance criteria, only 1 hour of Chinese data could be retained. This limited yield underscores both the shortage of usable Chinese medical speech resources and the value of the Chinese subset included in this corpus.

Given the size and composition of the Chinese subset, it should be understood as a complement to the English-dominant corpus rather than as a parallel monolingual benchmark. The corpus is therefore better suited for studying bilingual or code-mixed speech de-identification under a unified processing framework than for drawing strong conclusions about language-specific performance in Chinese alone. With multilingual foundation models such as Whisper 30 and Qwen3-ASR 31 increasingly capable of processing multiple languages within a single pipeline, the corpus may support future studies that jointly examine ASR and SHI recognition performance. However, quantitative comparisons between the unified bilingual system and language-specific alternatives are beyond the scope of the present corpus construction study and should be explored in future work.

Finally, although our controlled corpus construction design offers practical advantages for data sharing while reducing the ethical and privacy risks associated with releasing real patient-clinician conversations, it should be noted that the corpus was not collected from naturally occurring clinical encounters. Instead, it was constructed from rephrased clinicalstyle scripts, controlled re-recordings and drama-derived clinical-style dialogues. As a result, it may not fully capture the spontaneity, acoustic variability, interruptions, overlapping speech, emotional dynamics and interactional complexity commonly observed in real clinical conversations. The corpus is therefore best understood as a controlled clinical-style speech resource for developing and evaluating speech deidentification methods, rather than as a fully representative sample of real-world clinical communication. Accordingly, findings derived from this corpus should not be directly extrapolated to real-world clinical deployment. Future work should incorporate naturally occurring clinical recordings, where feasible and ethically permissible, to further improve ecological validity and generalisability. We make no claims regarding pooled multilingual evaluation, cross-lingual transfer or real-world deployment performance; these settings remain important directions for future investigation.
